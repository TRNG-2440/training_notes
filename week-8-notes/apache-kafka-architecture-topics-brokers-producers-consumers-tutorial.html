2. What is Apache Kafka?

Apache Kafka is a distributed event-streaming platform used to publish, store, read and process continuous streams of events across multiple machines.

What is an event?

An event is a statement that something happened. It commonly contains:

Key

CUST-104

Used for partition selection and grouping related events.

Value

{"status":"PAID"}

The business data.

Timestamp

2026-07-28T10:15:00Z

When the event occurred or was appended.

Headers

source=checkout

Optional metadata.

Common use cases

  • Order, payment and shipment event pipelines
  • Application logs and observability
  • IoT sensor streams
  • Database change data capture
  • Real-time fraud detection and analytics

3. Kafka Architecture Overview

Architecture in one sentence

Producers send events to a named topic; Kafka divides that topic into partitions; brokers store and serve those partitions; consumers read partitions and track progress using offsets.

4. Producer

A Producer is a client application that publishes events to Kafka topics.

Chooses the topic

Example: orders, payments or shipments.

Selects a partition

Usually based on a message key, explicit partition or partitioner strategy.

Sends records in batches

Batching and compression can improve throughput.

5. Topic

A Topic is a named logical stream or category into which related events are published.

Examples: orders, payments, customer-events, website-clicks.

A topic is not one computer, one directory or one broker. It is an abstraction that may be divided into many partitions and distributed across multiple brokers.

Topic: orders

Partition 0ORDER-100, ORDER-103, ORDER-106…
Partition 1ORDER-101, ORDER-104, ORDER-107…
Partition 2ORDER-102, ORDER-105, ORDER-108…

Important topic properties

  • Partition count: controls how many independent ordered logs the topic has.
  • Replication factor: controls how many broker copies each partition has.
  • Retention: controls how long or how much data Kafka keeps.
  • Cleanup policy: commonly deletion by time/size or log compaction.

6. Partitions and Offsets

A topic is split into partitions. Each partition is an append-only ordered log.

Why partitions?

  • Parallel reads and writes
  • Horizontal scalability
  • Distribution across brokers
  • Independent ordered logs

Message keys

Records with the same key are normally routed consistently to the same partition, supporting ordered processing for that key.

customerId=C101 → same partition for that customer.

Important: Increasing a topic’s partition count later can change key-to-partition mapping. Plan partition counts carefully.

7. Broker

A Broker is a running Kafka server process. Multiple brokers together form a Kafka cluster.

Stores partitions

A broker stores leader and follower replicas from many topics.

Handles requests

Receives producer writes and serves consumer fetch requests.

Replicates data

Follower replicas copy partition data from leaders.

One broker can store many topics

Broker 2

orders-P1 leader orders-P0 follower payments-P0 leader shipments-P2 follower clickstream-P4 leader

A broker is identified by a node ID and network listeners. Clients connect using bootstrap broker addresses and then discover the full cluster metadata.

9. Consumer

A Consumer is a client application that reads events from Kafka topics.

Consumer responsibilities

  • Subscribe to one or more topics or directly assign partitions.
  • Fetch records from partition leaders.
  • Deserialize keys and values.
  • Process the business event.
  • Commit or manage offsets to record processing progress.
Consumer pull model: Consumers request data from brokers at their own pace. This helps different applications process the same topic independently.

10. Consumer Groups and Parallelism

Consumers using the same group.id form a consumer group. Within a group, a partition is assigned to only one consumer at a time.

Fewer consumers than partitions

Some consumers receive multiple partitions.

More consumers than partitions

Extra consumers remain idle because one partition cannot be divided among multiple consumers in the same group at the same time.

Different groups get independent copies

The fraud-service group and the analytics-service group may both consume every event from the payments topic independently.

11. Replication, Leaders and Followers

Each partition may have multiple replicas on different brokers. One replica is the leader; other replicas are followers.

Key terms

  • Leader: the replica that normally handles client reads and writes for that partition.
  • Follower: copies records from the leader.
  • ISR: in-sync replicas sufficiently caught up with the leader.
  • Replication factor: total number of replicas for each partition.
Replication factor cannot exceed the number of available brokers used for distinct replicas.

12. KRaft Controllers and Cluster Metadata

Modern Kafka uses KRaft for metadata management. Kafka server processes may be configured as brokers, controllers or both in small development deployments.

Broker role

Stores topic partitions and handles producer/consumer data requests.

process.roles=broker

Controller role

Participates in the metadata quorum and manages cluster metadata and leadership decisions.

process.roles=controller
Do not confuse controller and broker. A controller manages metadata; a broker stores and serves event data. A development node may combine both roles, but critical deployments normally separate them.

13. Complete Message Journey

  1. Producer creates an event: for example, orderId=O9001.
  2. Producer discovers metadata: it connects to bootstrap brokers and learns which broker leads each partition.
  3. Partition is selected: the producer uses the key or partitioning logic.
  4. Leader broker receives the record: the record is appended to the selected partition log.
  5. Followers replicate: copies are maintained according to the replication setup.
  6. Producer receives acknowledgement: behavior depends on reliability configuration.
  7. Consumer group assignment occurs: each partition is assigned to one consumer in the group.
  8. Consumer fetches and processes: the record is deserialized and business logic runs.
  9. Offset advances: the consumer records how far it has processed.

15. Essential Kafka Commands

Commands use the modern --bootstrap-server style. On Windows distributions, use the matching scripts under bin\windows\.

Create a topic

bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create \
  --topic orders \
  --partitions 3 \
  --replication-factor 1

List topics

bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

Describe a topic

bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --describe \
  --topic orders

Start a console producer

bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 \
  --topic orders

Start a console consumer

bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic orders \
  --from-beginning \
  --group order-processing-group

View consumer-group offsets and lag

bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --describe \
  --group order-processing-group
Production note: A replication factor of 1 is only for a simple local demonstration. Real deployments normally use replication across brokers based on availability requirements.

16. Common Misunderstandings

Incorrect ideaCorrect explanation
“A topic is a server.”A topic is a logical event stream. Brokers are servers.
“One topic belongs to one broker.”A topic’s partitions and replicas can be distributed across many brokers.
“A broker stores only one topic.”A broker commonly stores partition replicas from many topics.
“Kafka guarantees global ordering.”Kafka guarantees ordering within a partition, not across all partitions of a topic.
“Adding more consumers always increases speed.”Within a group, useful parallelism is bounded by the number of assigned partitions.
“Consumers delete records after reading.”Consumption does not normally delete records; retention/compaction policies manage stored data.
“Bootstrap servers must list every broker.”The list is used for initial discovery; clients learn cluster metadata after connecting.
“A follower receives producer writes directly.”Clients normally communicate with the partition leader; followers replicate from it.

17. Architecture Best Practices

Topic design

  • Use meaningful domain-based topic names.
  • Define schemas and compatibility rules.
  • Choose retention and cleanup policies deliberately.
  • Avoid uncontrolled topic auto-creation in production.

Partition design

  • Use stable business keys when ordering by entity matters.
  • Estimate throughput and consumer parallelism.
  • Avoid very hot keys that overload one partition.
  • Remember that partition count is difficult to reduce.

Broker design

  • Spread replicas across failure domains.
  • Monitor disk, network, request latency and under-replicated partitions.
  • Balance partition leaders and storage across brokers.
  • Use multiple bootstrap addresses for resilience.

Consumer design

  • Make processing idempotent where duplicates are possible.
  • Commit offsets only according to a deliberate processing strategy.
  • Monitor consumer lag.
  • Handle rebalances and processing failures safely.

18. Interview Questions and Answers

1. What is Apache Kafka?

A distributed event-streaming platform that enables applications to publish, store, consume and process streams of events across a cluster.

2. What is a Kafka topic?

A named logical stream/category of events. A topic is divided into partitions.

3. What is a Kafka broker?

A running Kafka server process that stores partition replicas and handles producer, consumer and administrative requests.

4. What is the key difference between a topic and broker?

A topic is a logical organization of events; a broker is infrastructure that physically stores and serves topic partitions.

5. Can one topic exist on multiple brokers?

Yes. Its partitions and replicas can be spread across multiple brokers.

6. Can one broker store multiple topics?

Yes. One broker normally stores replicas from many topics and partitions.

7. What is a partition?

An ordered, append-only log that forms one shard of a topic.

8. What is an offset?

A sequential position of a record within a partition. Consumers use offsets to track progress.

9. Where is ordering guaranteed?

Within one partition. Kafka does not provide a single total order across all partitions of a topic.

10. What does a producer do?

Serializes and publishes records to a topic, selecting a partition and sending the record to the appropriate leader broker.

11. What does a consumer do?

Fetches records from topic partitions, deserializes them, performs processing and manages offsets.

12. What is a consumer group?

A set of consumers sharing a group ID. Topic partitions are divided among active consumers in that group.

13. Why can an extra consumer remain idle?

Because a partition can be assigned to only one consumer in a group at a time. If consumers exceed partitions, some receive no partition.

14. What is a partition leader?

The replica that handles normal client reads and writes for the partition.

15. What is a follower replica?

A copy that fetches data from the leader and may become leader after a failure when eligible.

16. What is ISR?

The set of in-sync replicas that are sufficiently caught up with the leader.

17. What is replication factor?

The number of replicas maintained for each partition.

18. What are bootstrap servers?

Initial broker addresses used by clients to connect and discover cluster metadata. They do not have to include every broker.

19. What is consumer lag?

The difference between the latest available offset and the consumer group’s processed or committed position.

20. What is KRaft?

Kafka’s Raft-based metadata management mode, using a controller quorum instead of a separate ZooKeeper ensemble.

21. Why use a message key?

To influence partition selection and keep related entity events, such as all events for one order, in a consistent partition.

22. Does reading an event remove it from Kafka?

No. Kafka retains events according to topic retention or compaction settings, independently of consumer reads.
