2. Messaging foundation

Both technologies decouple producers from consumers. A producer sends an event without directly calling every downstream system.

Event example: OrderCreated may contain order ID, customer ID, restaurant, total amount, timestamp and delivery location.

3. Apache Kafka architecture

Kafka is a distributed event-streaming platform. Events are written to named topics, divided into partitions and stored by brokers. Consumers normally track their reading position through offsets.

Important Kafka terms

TermMeaningReal-world analogy
BrokerA Kafka server that stores topic partitions and serves clients.A warehouse building.
TopicA named stream/category of events.A labelled warehouse aisle.
PartitionAn ordered append-only portion of a topic.One conveyor belt.
OffsetThe position of an event inside a partition.A serial number on the belt.
Consumer groupConsumers cooperating to divide partitions.Workers sharing conveyor belts.
ReplicationCopies of partitions maintained on multiple brokers.Backup warehouse copies.

4. Google Cloud Pub/Sub architecture

Pub/Sub is a fully managed asynchronous messaging service. Publishers send messages to a topic. Each subscription represents an independent delivery path from that topic to a subscriber.

Critical idea: A Pub/Sub topic does not deliver directly to a subscriber application. Delivery happens through a subscription. One topic can feed multiple subscriptions.
TermMeaning
TopicThe named resource to which publishers send messages.
SubscriptionAn independent stream of messages from one topic to subscriber clients.
AcknowledgementThe subscriber confirms successful processing.
Pull deliveryThe subscriber requests or streams messages from Pub/Sub.
Push deliveryPub/Sub sends an HTTPS request to the subscriber endpoint.
Dead-letter topicA destination for messages that cannot be processed after configured attempts.

5. Kafka vs Pub/Sub: core differences

DimensionApache KafkaGoogle Cloud Pub/Sub
Primary modelDistributed, durable event log.Fully managed publish/subscribe messaging.
InfrastructureYou operate brokers, or use a managed Kafka provider.Google manages the messaging infrastructure.
Scaling unitPartitions, brokers, storage and consumer-group members.Service scales without exposing brokers or partition administration.
Consumer positionConsumers use partition offsets.Subscriber delivery state is managed through subscriptions and acknowledgements.
OrderingOrdering is naturally maintained within a partition.Ordering can be enabled with ordering keys; it is not a single global order.
ReplayConsumers can seek to earlier offsets while retained data remains.Replay uses retained messages, seek/snapshots or re-delivery mechanisms.
PortabilityStrong portability across on-premises and clouds through the Kafka ecosystem.Native Google Cloud API and operational model.
Processing ecosystemKafka Streams, Kafka Connect, ksqlDB ecosystem and many connectors.Strong integrations with Dataflow, Cloud Run, Functions, BigQuery and other GCP services.
Best fitEvent streaming platform, long-lived logs, Kafka compatibility and fine-grained control.Rapid cloud-native event delivery with minimal operational burden.
Do not compare only by throughput. The most important distinction is the operating and programming model: Kafka exposes a distributed log; Pub/Sub exposes a managed topic-and-subscription service.

6. Real-world case study: food-delivery platform

A food-delivery company receives thousands of order events. Payment, restaurant assignment, delivery tracking, customer notification, fraud detection and analytics all need the same order information.

Business event

{
  "eventType": "OrderCreated",
  "orderId": "ORD-90031",
  "customerId": "CUS-1044",
  "restaurantId": "RES-210",
  "city": "Chennai",
  "amount": 785.50,
  "eventTime": "2026-08-04T12:30:00+05:30"
}
Payment
Authorize the amount and publish payment status.
Notification
Send confirmation through email, SMS or mobile push.
Analytics
Calculate orders per city, revenue and restaurant performance.
Fraud
Detect unusual order values or rapid repeated purchases.

Why asynchronous messaging?

The order API can respond quickly after storing the order and publishing an event. Slow analytics or notification services do not have to block the customer transaction.

8. Delivery, duplicates, ordering and replay

At-least-once thinking

Applications should normally be designed to tolerate duplicate delivery. A safe consumer is idempotent: processing the same event twice does not produce two payments or two inventory deductions.

# Simplified idempotency logic
if event_id already exists in processed_events:
    return "already processed"

begin transaction
perform_business_operation()
insert event_id into processed_events
commit transaction

Ordering

RequirementKafka approachPub/Sub approach
Orders for one customer must remain orderedUse customer ID as the record key so related events enter the same partition.Use customer ID as an ordering key and enable ordered delivery on the subscription.
All global events must have one strict orderOne partition can provide it, but limits parallelism.Global total ordering is generally not the normal scalable design.

Replay

Kafka replay commonly means resetting or seeking consumer offsets. Pub/Sub replay depends on message retention and subscription features such as seek and snapshots. In either system, replaying into a non-idempotent consumer can repeat side effects.

10. Kafka choices on Google Cloud

On GCP, “Kafka” can mean several different deployments:

Self-managed Kafka on Compute Engine or GKE
Maximum control, maximum operations.
Google Cloud Managed Service for Apache Kafka
Native managed Kafka clusters with Kafka compatibility while Google automates major cluster tasks.
Third-party managed Kafka
A Kafka provider operates clusters, often with rich connector and governance tooling.
Cloud Pub/Sub
Use the GCP-native messaging API instead of the Kafka protocol.
Migration question: If an existing application depends on Kafka clients, offsets, Kafka Connect or Kafka Streams, managed Kafka may reduce migration changes. For a new GCP-native serverless application, Pub/Sub may be simpler.

11. Decision guide

RequirementRecommended starting pointReason
Existing Kafka applications and connectorsManaged KafkaPreserves Kafka protocol and ecosystem compatibility.
New Cloud Run microservices with minimal operationsPub/SubNative managed delivery and straightforward GCP integration.
Hybrid/on-premises and multi-cloud portabilityKafkaKafka is widely deployable across environments.
Fine control over partitions, offsets and log retentionKafkaThese are first-class Kafka concepts.
Webhook-style event deliveryPub/Sub push subscriptionPub/Sub can initiate HTTPS delivery.
Stream processing tightly coupled to Kafka topicsKafka plus Kafka StreamsNative Kafka processing model.
GCP data pipeline to Dataflow/BigQueryPub/SubStrong native integrations and low operations.

Five-question checklist

  1. Must the application remain Kafka-protocol compatible?
  2. Does the team want control over partitions and offsets?
  3. Is multi-cloud or on-premises portability essential?
  4. How much operational work can the team accept?
  5. Which downstream services and processing frameworks are required?

12. Hands-on: Google Cloud Pub/Sub demo

Scenario: Publish food-order events and consume them using a pull subscription.

Prerequisites

  • A Google Cloud project with billing as required.
  • Cloud Shell or a local machine with Google Cloud CLI.
  • Pub/Sub API enabled and suitable IAM permissions.

Step 1 — Configure the project

gcloud auth login
gcloud config set project YOUR_PROJECT_ID
gcloud services enable pubsub.googleapis.com

Step 2 — Create a topic and subscription

gcloud pubsub topics create order-events

gcloud pubsub subscriptions create order-processing-sub \
  --topic=order-events

Step 3 — Publish messages

gcloud pubsub topics publish order-events \
  --message='{"orderId":"ORD-1001","city":"Chennai","amount":550}'

gcloud pubsub topics publish order-events \
  --message='{"orderId":"ORD-1002","city":"Bengaluru","amount":820}'

Step 4 — Pull messages

gcloud pubsub subscriptions pull order-processing-sub \
  --auto-ack \
  --limit=10

Python publisher

from google.cloud import pubsub_v1
import json

project_id = "YOUR_PROJECT_ID"
topic_id = "order-events"

publisher = pubsub_v1.PublisherClient()
topic_path = publisher.topic_path(project_id, topic_id)

order = {
    "orderId": "ORD-2001",
    "city": "Chennai",
    "amount": 799.50
}

future = publisher.publish(
    topic_path,
    json.dumps(order).encode("utf-8"),
    eventType="OrderCreated"
)

print("Published message ID:", future.result())

Python subscriber

from google.cloud import pubsub_v1

project_id = "YOUR_PROJECT_ID"
subscription_id = "order-processing-sub"

subscriber = pubsub_v1.SubscriberClient()
subscription_path = subscriber.subscription_path(
    project_id, subscription_id
)

def callback(message):
    try:
        print("Order received:", message.data.decode("utf-8"))
        print("Attributes:", dict(message.attributes))
        message.ack()
    except Exception:
        message.nack()

streaming_pull_future = subscriber.subscribe(
    subscription_path,
    callback=callback
)

print("Listening...")
try:
    streaming_pull_future.result()
except KeyboardInterrupt:
    streaming_pull_future.cancel()

Install and authenticate locally

pip install google-cloud-pubsub
gcloud auth application-default login

13. Small Kafka demo for comparison

This example assumes a reachable Kafka broker at localhost:9092 and an order-events topic.

Install Python client

pip install confluent-kafka

Producer

from confluent_kafka import Producer
import json

producer = Producer({"bootstrap.servers": "localhost:9092"})

order = {
    "orderId": "ORD-3001",
    "customerId": "CUS-101",
    "city": "Chennai",
    "amount": 925
}

producer.produce(
    "order-events",
    key=order["customerId"],
    value=json.dumps(order)
)
producer.flush()
print("Order published")

Consumer

from confluent_kafka import Consumer

consumer = Consumer({
    "bootstrap.servers": "localhost:9092",
    "group.id": "payment-service",
    "auto.offset.reset": "earliest"
})

consumer.subscribe(["order-events"])

try:
    while True:
        message = consumer.poll(1.0)
        if message is None:
            continue
        if message.error():
            print(message.error())
            continue
        print("Order:", message.value().decode("utf-8"))
finally:
    consumer.close()
Observe the conceptual difference: Kafka configures a broker address and consumer group. Pub/Sub configures a Google Cloud project, topic and subscription.

14. Hybrid architecture: Kafka and Pub/Sub together

Large organisations sometimes use both. Kafka may remain the enterprise event backbone while Pub/Sub distributes selected events to GCP-native workloads.

Use a bridge only when there is a real integration need. Every bridge introduces schema mapping, monitoring, security, duplicate-handling and failure-recovery responsibilities.

15. Common problems and troubleshooting

SymptomLikely causeAction
Kafka consumer receives nothingWrong topic, broker, group position or network connectivity.Verify topic, bootstrap servers, offsets, ACLs and consumer logs.
Kafka lag continuously growsConsumer processing is slower than production.Add suitable partitions/consumers, batch work, optimise processing or reduce downstream latency.
Pub/Sub permission deniedMissing IAM role for publisher or subscriber identity.Verify service account and topic/subscription-level permissions.
Pub/Sub messages are redeliveredNo acknowledgement, deadline exceeded or consumer failure.Acknowledge only after success, tune flow control and make processing idempotent.
Ordering appears inconsistentDifferent Kafka partitions or different/missing Pub/Sub ordering keys.Use a stable business key and understand ordering scope.
Duplicate paymentConsumer repeated a non-idempotent side effect.Use event IDs, uniqueness constraints and transactional idempotency.

16. Interview questions and answers

1. Topic vs broker?
A topic is a logical event stream; a broker is a Kafka server that stores topic partitions.
2. Topic vs subscription in Pub/Sub?
Publishers write to a topic. Subscribers consume through subscriptions, each with independent delivery state.
3. Why use partitions in Kafka?
Partitions provide scalable parallelism, distribution and ordering within each partition.
4. Why can duplicates occur?
A message may be delivered again when acknowledgement or commit status is uncertain.
5. What is consumer lag?
The difference between the latest available Kafka offset and a consumer group's processed position.
6. What is a dead-letter topic?
A destination for messages that repeatedly fail processing.
7. When is Kafka preferred?
When Kafka compatibility, event-log control, connectors, offsets or portability are important.
8. When is Pub/Sub preferred?
For GCP-native asynchronous messaging with low infrastructure management.
9. Does one topic equal one consumer?
No. Kafka supports multiple consumer groups; Pub/Sub supports multiple subscriptions.
10. What is idempotency?
The ability to process the same event more than once without repeating the business effect.
11. Push vs pull?
Push sends HTTPS requests to a consumer endpoint; pull lets consumers request or stream messages.
12. Can both coexist?
Yes. A bridge can connect Kafka ecosystems to GCP-native Pub/Sub consumers.
13. What controls Kafka ordering?
Partition assignment; records in a partition have an ordered sequence.
14. What controls Pub/Sub ordering?
Ordering keys and ordered-delivery configuration.
15. Main operational difference?
Kafka exposes cluster resources and partitions; Pub/Sub hides most infrastructure management.
