2. Before Airflow: What Is a Workflow?

A workflow is an ordered set of activities that together achieve a business outcome. A data pipeline is a workflow that moves or transforms data. Orchestration coordinates these activities: what runs, when it runs, what must finish first, what happens after failure, and how operators observe the result.

Validate
→
Transform
→
Warehouse

Orchestration versus execution

ResponsibilityExample toolMeaning
OrchestrationAirflowCoordinates task dependencies, schedules, retries, state, alerts, and observability.
Data processingSpark, SQL, dbt, PythonPerforms transformations and computation.
Streaming transportKafka / Pub/SubMoves events continuously between producers and consumers.
StorageS3, ADLS, GCS, warehousePersists input, intermediate, and output data.
Important: Airflow is normally the conductor, not the entire orchestra. Heavy processing should run in a suitable compute engine instead of inside the scheduler.

3. Traditional Approaches: What Existed Before Airflow?

Common traditional approaches

  • Manual execution by an operator.
  • Operating-system Cron jobs or Windows Task Scheduler.
  • Large shell or PowerShell scripts.
  • Database stored procedures triggered by SQL Agent.
  • Custom Python scheduler loops.
  • Enterprise batch schedulers maintained by a central operations team.

Why they initially worked

  • Easy for one script and one schedule.
  • Already available with the operating system.
  • Low setup effort.
  • Suitable for a small team with few dependencies.

Traditional nightly pipeline example

# Pseudo batch script
python download_sales.py
if errorlevel 1 exit /b 1

python clean_sales.py
if errorlevel 1 exit /b 1

python load_warehouse.py
if errorlevel 1 exit /b 1

python send_report.py

Drawbacks as the system grows

ProblemTraditional impactHow Airflow helps
Hidden dependenciesOrder exists only inside scripts or human knowledge.DAG graph explicitly represents upstream and downstream relationships.
Poor retry controlWhole script reruns even when only one step failed.Retry or clear an individual task instance.
Weak observabilityLogs are scattered across servers.Central UI shows DAG runs, task states, logs, duration, and history.
No backfill modelOperators manually calculate missed dates.Scheduled logical dates and controlled historical runs.
Configuration sprawlPasswords and paths are hard-coded.Connections, variables, environment configuration, and secrets backends.
Scaling difficultyOne server becomes a bottleneck.Pluggable executors and distributed workers.
Change riskScripts changed directly on servers.DAGs are source-controlled Python code.
Resource contentionToo many jobs hit the same database.Pools, concurrency settings, priorities, and queues.
Analogy: Cron is an alarm clock. Airflow is an operations control room that knows the full plan, dependencies, status, retry rules, and history.

4. Apache Airflow Introduction

Apache Airflow is an open-source platform for programmatically authoring, scheduling, and monitoring workflows. Workflows are expressed as Python code, making them easier to version, review, test, and reuse.

What Airflow does

Author

Define workflow structure and configuration in Python.

Schedule

Run by time, timetable, asset update, API trigger, or external event pattern.

Execute

Submit runnable task instances through an executor to workers.

Monitor

Inspect states, logs, duration, retries, dependencies, and failures.

What Airflow is not

  • It is not primarily a real-time stream-processing engine.
  • It is not a data warehouse or database.
  • It is not a replacement for Spark, Kafka, dbt, or cloud storage.
  • It is not ideal for millisecond event processing.
  • It should not be used to pass large datasets through XCom.

Typical users

Data engineers, analytics engineers, ML engineers, platform engineers, DevOps teams, and application teams use Airflow to coordinate multi-step work across databases, cloud services, APIs, containers, data lakes, warehouses, and reporting platforms.

5. Benefits, Good Fit, and Poor Fit

Maintainability

Workflow code can be modular, reviewed, versioned, and tested.

Reliability

Retries, timeouts, dependency checks, trigger rules, and idempotent reruns.

Visibility

Graph, Grid, task logs, run history, and operational state.

Scalability

Local, Celery, Kubernetes, and other executor models.

Extensibility

Providers, hooks, operators, sensors, custom plugins, REST API.

Governance

Central control of schedules, access, connections, pools, and deployments.

Use Airflow when

  • The workflow has multiple dependent steps.
  • Failures must be retried or investigated at task level.
  • Historical runs and reruns matter.
  • Many tools must be coordinated.
  • Teams require central visibility and operational standards.

Do not choose Airflow as the main engine when

  • You need sub-second continuous event processing.
  • You only have one simple command with no dependency or observability requirement.
  • A product-specific scheduler already fully solves the use case.
  • You intend to run large in-memory transformation workloads directly inside Airflow processes.

6. Airflow Architecture

Component responsibilities

ComponentResponsibilityIndustry note
DAG ProcessorReads Python DAG files and produces parsed/serialized workflow definitions.Keep top-level DAG code lightweight to reduce parsing load.
SchedulerCreates runs and identifies task instances whose dependencies and scheduling conditions are satisfied.Persistent service; production setups monitor heartbeats and health.
Metadata databaseStores operational state such as DAG runs, task instances, configuration metadata, and history.Use a production-supported database and maintain backups.
ExecutorDetermines how runnable tasks are dispatched.Executor choice affects scale, isolation, cost, and operations.
WorkerRuns task code.Tasks may run on different machines; avoid local-only assumptions.
API server / UIProvides web interaction and API access.Secure through authentication, authorization, TLS, and network controls.
TriggererRuns lightweight asynchronous triggers for deferrable tasks.Prevents long waits from occupying expensive worker slots.

End-to-end lifecycle

1. Author: A developer places a Python DAG file in the DAG location.
2. Parse: The DAG Processor imports and serializes the workflow definition.
3. Schedule: The Scheduler determines whether a DAG run should be created.
4. Evaluate: Dependencies, trigger rules, pools, concurrency, and task state are checked.
5. Queue: Runnable task instances are handed to the configured Executor.
6. Execute: A Worker runs the task and records logs and status.
7. Continue: Downstream tasks become runnable when conditions are satisfied.
8. Observe: Users inspect state through UI, API, metrics, alerts, and logs.

7. DAGs: Directed Acyclic Graphs

A DAG is the model of a workflow. It contains tasks, their dependencies, schedule, callbacks, and operational configuration.

Directed

Dependencies point from upstream to downstream.

Acyclic

The graph cannot loop back to an earlier task.

Graph

Tasks are nodes; dependency relationships are edges.

Simple DAG structure

extract
→
validate
→
transform
→
load

TaskFlow DAG example

import pendulum
from airflow.sdk import dag, task

@dag(
    dag_id="hello_airflow",
    schedule=None,
    start_date=pendulum.datetime(2026, 1, 1, tz="UTC"),
    catchup=False,
    tags=["training"],
)
def hello_airflow():

    @task
    def greet():
        return "Hello from Apache Airflow"

    @task
    def display(message: str):
        print(message)

    display(greet())

hello_airflow()

Key DAG parameters

ParameterPurposeRecommendation
dag_idUnique logical workflow name.Use stable, descriptive, lowercase names.
scheduleDefines when or under what condition the DAG runs.Use explicit schedules and document business timezone.
start_dateBeginning of scheduling calculation.Use a fixed, timezone-aware date, not dynamic “now”.
catchupControls creation of historical scheduled runs.Usually disable during learning; enable deliberately for backfills.
tagsClassifies DAGs in the UI.Tag by team, domain, environment, or business function.
default_argsReusable task defaults such as retries.Use consistent operational policies.

Dependency syntax

extract >> validate >> transform >> load

# Fan-out
extract >> [validate_schema, validate_quality]

# Fan-in
[load_customers, load_orders] >> publish_report
DAG definition versus DAG run: The DAG is the blueprint. A DAG run is one execution of that blueprint for a specific logical time or trigger.

8. Operators: Reusable Task Templates

An Operator represents a predefined kind of work. When an Operator is placed in a DAG, it becomes a task definition.

Main categories

CategoryPurposeExamples
Action operatorsPerform work.Python task, Bash task, SQL execution, cloud job submission.
Transfer operatorsMove data between systems.Object storage to warehouse, database to cloud storage.
SensorsWait until a condition is true.File arrival, external task completion, object existence.
Branching operatorsSelect a path based on logic.Quality pass/fail, weekday/weekend, threshold routing.
Human-in-the-loopPause for an explicit human decision.Approval before production release or financial publication.

Classic BashOperator example for Airflow 3

from airflow.providers.standard.operators.bash import BashOperator

print_date = BashOperator(
    task_id="print_date",
    bash_command="date",
)

Operator versus TaskFlow

Classic Operator styleTaskFlow style
Explicit Operator object.Python function decorated with @task.
Dependencies commonly use >>.Dependencies can be inferred from function arguments.
Manual XCom handling may be required.Function return values are passed through XCom automatically.
Excellent for provider-specific integrations.Excellent for readable Python-centric workflows.
Industry pattern: Prefer existing provider operators and hooks before writing a custom integration. Create a custom Operator when the behavior is reusable across many DAGs and has a clear interface.

9. Tasks and Task Instances

A task is a unit of work defined in a DAG. A task instance is that task running—or waiting to run—inside a specific DAG run.

Blueprint analogy

Task definition

“Validate today’s sales file.” This is part of the workflow blueprint.

Task instance

“Validate the sales file for the July 29, 2026 DAG run.” This has a state, attempt number, logs, and duration.

Common task states

StateMeaningOperator action
scheduledScheduler has determined the task should run.Usually wait.
queuedWaiting for executor/worker capacity.Check pools, queues, workers, and concurrency if delayed.
runningWorker is executing the task.Inspect live logs and duration.
successCompleted successfully.No action.
failedExecution failed.Inspect logs, fix root cause, retry or clear safely.
up_for_retryFailed but retry policy allows another attempt.Check whether the error is transient.
skippedNot selected due to branching or trigger logic.Confirm expected path.
deferredWaiting asynchronously through the Triggerer.Check trigger conditions and triggerer health.
upstream_failedCould not run because an upstream dependency failed.Fix the upstream failure first.

Retries and timeout example

from datetime import timedelta
from airflow.sdk import task

@task(
    retries=3,
    retry_delay=timedelta(minutes=5),
    execution_timeout=timedelta(minutes=30),
)
def call_partner_api():
    # Raise an exception on failure.
    # Airflow records the attempt and applies retry policy.
    pass
Idempotency: A task should produce the same correct result when safely rerun for the same logical input. For example, overwrite a date partition or use an upsert instead of blindly appending duplicates.

10. Scheduler Deep Dive

The Scheduler continuously monitors DAGs and task state. It creates scheduled runs and triggers task instances after their dependencies and resource conditions are satisfied. The configured Executor performs the dispatch.

Scheduler decision checklist

  1. Is the DAG active and due to run?
  2. Does a DAG run exist for the logical interval?
  3. Are all required upstream task states acceptable?
  4. Does the task’s trigger rule allow execution?
  5. Are DAG and task concurrency limits available?
  6. Does the assigned pool have free slots?
  7. Is the task queue and priority eligible?
  8. Can the Executor accept more work?

Schedule concepts

ConceptExplanation
Logical dateThe logical label for a DAG run. It is not simply “the exact wall-clock time the task began.”
Data intervalThe time range of data that the run is expected to process.
CatchupCreates missed scheduled intervals from the start date to the current schedule, when enabled.
BackfillIntentional execution of historical intervals.
Manual triggerA user or API explicitly creates a run.
Asset/event triggerA data or external event causes a run rather than only a clock schedule.

Cron examples

ExpressionMeaning
0 6 * * *Every day at 06:00.
0 */4 * * *Every four hours.
30 8 * * 1-5Weekdays at 08:30.
0 2 1 * *First day of each month at 02:00.
Common scheduling mistake: Using a dynamic start_date such as the current timestamp can prevent predictable scheduling. Use a fixed timezone-aware start date.

11. Executors and Scaling

The Executor is the mechanism that runs task instances. It influences where tasks execute and how the platform scales.

Executor patternBest fitTrade-offs
Local executionLearning, development, smaller single-node deployments.Simple, but limited isolation and horizontal scaling.
Celery-based distributed workersLong-running worker fleet and mixed workloads.Scales horizontally but requires broker, workers, and operational management.
Kubernetes-based task podsCloud-native isolation and elastic workloads.Strong isolation and elasticity; Kubernetes complexity and startup overhead.
Managed Airflow serviceTeams that want reduced platform operations.Convenience and support versus service constraints and cost.

Scaling controls beyond the executor

  • Global parallelism.
  • DAG-level active run limits.
  • Task concurrency controls.
  • Pools and pool slots.
  • Queue routing.
  • Worker autoscaling.
  • Priority weights.
Queue delay diagnosis: Runnable but queued usually points to capacity, pool, executor, worker, or concurrency constraints—not necessarily faulty task code.

12. Supporting Concepts You Need in Real Projects

Sensors and deferrable tasks

Sensors wait for conditions such as a file, object, partition, or external task. Traditional “poke” mode holds a worker slot while waiting. Reschedule mode releases the slot between checks. Deferrable operators suspend themselves and move waiting logic to the Triggerer, freeing workers.

XCom

XCom is task-to-task metadata exchange. It is designed for small values such as IDs, counts, paths, and compact dictionaries—not full DataFrames or large files.

@task
def extract() -> dict:
    return {"file_path": "/data/orders.csv", "row_count": 25000}

@task
def validate(metadata: dict):
    print(metadata["row_count"])

Variables, Connections, and secrets

FeatureUseGuideline
VariablesRuntime configuration values.Do not read many Variables in top-level DAG parsing code.
ConnectionsExternal service endpoints and credentials.Reference by connection ID through hooks/operators.
Secrets backendCentral secret manager integration.Prefer it for production credentials.

Pools

Pools limit concurrent access to constrained resources. Example: a legacy database supports only five parallel heavy queries, so tasks use a pool with five slots.

Trigger rules

Rule ideaUse case
All upstream succeededNormal sequential processing.
At least one upstream succeededJoin after optional branches.
All upstream completedCleanup task must run after success or failure.
One upstream failedFailure notification or compensating action.

TaskGroups

TaskGroups visually group related tasks without creating a separate scheduler boundary. Use them to simplify a large graph, such as grouping bronze, silver, and gold activities.

Assets

An asset represents a logical data object. Producer tasks can update assets, and downstream DAGs can be scheduled from those updates. This makes data-aware orchestration clearer than only using clock schedules.

Dynamic task mapping

Dynamic mapping creates task instances at runtime based on upstream data. Example: discover 20 customer files, then create 20 parallel processing task instances with expand().

16. Complete Hands-on Lab

Step 1: Create the DAG file

Create C:\AirflowLab\dags\retail_sales_pipeline.py and paste the following code.

from __future__ import annotations

import csv
import json
from collections import defaultdict
from datetime import timedelta
from decimal import Decimal, InvalidOperation
from pathlib import Path

import pendulum
from airflow.sdk import dag, task

BASE_DIR = Path("/opt/airflow/logs/retail_demo")
RAW_FILE = BASE_DIR / "raw_sales.csv"
SUMMARY_FILE = BASE_DIR / "daily_summary.json"
REPORT_FILE = BASE_DIR / "management_report.txt"


@dag(
    dag_id="retail_daily_sales_pipeline",
    schedule=None,  # Change to "0 6 * * *" after testing.
    start_date=pendulum.datetime(2026, 1, 1, tz="UTC"),
    catchup=False,
    tags=["training", "retail", "etl"],
    default_args={
        "retries": 2,
        "retry_delay": timedelta(minutes=1),
    },
)
def retail_daily_sales_pipeline():

    @task
    def create_sample_input() -> str:
        """Simulate the arrival of a store-sales file."""
        BASE_DIR.mkdir(parents=True, exist_ok=True)

        rows = [
            ["S1001", "BLR-01", "Electronics", 2, "499.50"],
            ["S1002", "BLR-01", "Grocery", 5, "12.25"],
            ["S1003", "CHN-01", "Electronics", 1, "799.00"],
            ["S1004", "CHN-01", "Home", 3, "85.40"],
            ["S1005", "HYD-01", "Grocery", 8, "9.75"],
            ["S1006", "HYD-01", "Home", 2, "120.00"],
        ]

        # Opening in write mode makes this task idempotent for reruns.
        with RAW_FILE.open("w", newline="", encoding="utf-8") as handle:
            writer = csv.writer(handle)
            writer.writerow(
                ["sale_id", "store_id", "category", "quantity", "unit_price"]
            )
            writer.writerows(rows)

        print(f"Created input file: {RAW_FILE}")
        return str(RAW_FILE)

    @task
    def validate_input(file_path: str) -> dict:
        """Validate schema, uniqueness, quantity, and price."""
        required_columns = {
            "sale_id", "store_id", "category", "quantity", "unit_price"
        }
        seen_sale_ids = set()
        valid_rows = 0

        with Path(file_path).open(newline="", encoding="utf-8") as handle:
            reader = csv.DictReader(handle)

            if set(reader.fieldnames or []) != required_columns:
                raise ValueError(
                    f"Invalid schema. Received: {reader.fieldnames}"
                )

            for line_number, row in enumerate(reader, start=2):
                sale_id = row["sale_id"].strip()
                store_id = row["store_id"].strip()
                category = row["category"].strip()

                if not sale_id or not store_id or not category:
                    raise ValueError(f"Blank mandatory field at line {line_number}")

                if sale_id in seen_sale_ids:
                    raise ValueError(f"Duplicate sale_id: {sale_id}")
                seen_sale_ids.add(sale_id)

                try:
                    quantity = int(row["quantity"])
                    unit_price = Decimal(row["unit_price"])
                except (ValueError, InvalidOperation) as exc:
                    raise ValueError(
                        f"Invalid numeric value at line {line_number}"
                    ) from exc

                if quantity <= 0 or unit_price < 0:
                    raise ValueError(
                        f"Quantity/price rule failed at line {line_number}"
                    )

                valid_rows += 1

        metadata = {"file_path": file_path, "valid_rows": valid_rows}
        print(f"Validation succeeded: {metadata}")
        return metadata

    @task
    def transform_and_load(metadata: dict) -> dict:
        """Aggregate revenue by category and write warehouse-ready JSON."""
        category_summary = defaultdict(
            lambda: {"quantity": 0, "revenue": Decimal("0.00")}
        )

        with Path(metadata["file_path"]).open(
            newline="", encoding="utf-8"
        ) as handle:
            reader = csv.DictReader(handle)
            for row in reader:
                category = row["category"].strip().title()
                quantity = int(row["quantity"])
                unit_price = Decimal(row["unit_price"])
                category_summary[category]["quantity"] += quantity
                category_summary[category]["revenue"] += (
                    quantity * unit_price
                )

        result = {
            category: {
                "quantity": values["quantity"],
                "revenue": str(values["revenue"].quantize(Decimal("0.01"))),
            }
            for category, values in sorted(category_summary.items())
        }

        with SUMMARY_FILE.open("w", encoding="utf-8") as handle:
            json.dump(result, handle, indent=2)

        total_revenue = sum(
            Decimal(values["revenue"]) for values in result.values()
        )

        summary_metadata = {
            "summary_file": str(SUMMARY_FILE),
            "category_count": len(result),
            "source_rows": metadata["valid_rows"],
            "total_revenue": str(total_revenue.quantize(Decimal("0.01"))),
        }
        print(json.dumps(summary_metadata, indent=2))
        return summary_metadata

    @task
    def quality_check(summary_metadata: dict) -> dict:
        """Check that output exists and totals are reasonable."""
        summary_path = Path(summary_metadata["summary_file"])
        if not summary_path.exists():
            raise FileNotFoundError(summary_path)

        if summary_metadata["source_rows"] < 1:
            raise ValueError("No valid source rows")

        if Decimal(summary_metadata["total_revenue"]) <= 0:
            raise ValueError("Total revenue must be positive")

        quality = {
            "status": "PASS",
            "checked_file": str(summary_path),
            "source_rows": summary_metadata["source_rows"],
        }
        print(quality)
        return quality

    @task
    def publish_report(summary_metadata: dict, quality: dict) -> str:
        """Write a small management report."""
        report = (
            "RETAIL DAILY SALES REPORT\n"
            "=========================\n"
            f"Quality status : {quality['status']}\n"
            f"Source rows    : {summary_metadata['source_rows']}\n"
            f"Categories     : {summary_metadata['category_count']}\n"
            f"Total revenue  : ${summary_metadata['total_revenue']}\n"
            f"Summary file   : {summary_metadata['summary_file']}\n"
        )
        REPORT_FILE.write_text(report, encoding="utf-8")
        print(report)
        return str(REPORT_FILE)

    raw_path = create_sample_input()
    validated = validate_input(raw_path)
    summary = transform_and_load(validated)
    quality = quality_check(summary)
    publish_report(summary, quality)

17. Advanced Patterns

17.1 Branching

from airflow.sdk import task

@task.branch
def choose_path(row_count: int) -> str:
    if row_count == 0:
        return "skip_processing"
    return "process_data"

17.2 Dynamic task mapping

from airflow.sdk import task

@task
def discover_files():
    return ["store_01.csv", "store_02.csv", "store_03.csv"]

@task
def process_file(file_name: str):
    print(f"Processing {file_name}")

process_file.expand(file_name=discover_files())

17.4 Setup and teardown tasks

Use setup and teardown relationships for temporary infrastructure, sessions, or resources. The teardown should run even when normal processing fails, subject to its trigger behavior.

17.5 Custom Operator

Create a custom Operator when many DAGs need the same reusable action with standardized logging, templating, validation, and connection handling.

17.6 Event-driven and message queue patterns

Airflow 3 supports event-oriented patterns, including external events and poll-based message queue triggers. Use them when the workflow reacts to meaningful events but still benefits from task-level orchestration. Use a streaming engine when every individual event must be processed with very low latency.

17.7 Task isolation

  • Virtual environment tasks for dependency isolation.
  • External Python tasks for a prebuilt interpreter.
  • Container or Kubernetes tasks for strong runtime isolation.
  • Remote Spark, Databricks, EMR, Dataproc, or warehouse jobs for heavy compute.

18. Production-Grade Airflow Standards

Architecture checklist

  • Production-supported metadata database.
  • Database backups and maintenance.
  • High-availability scheduler where required.
  • Remote logging and log retention.
  • Secrets backend.
  • TLS and network restrictions.
  • RBAC and least privilege.
  • Executor and worker sizing.
  • Health checks and alerting.
  • Metrics for scheduler, workers, queues, and DAGs.
  • Automated DAG deployment.
  • Disaster recovery plan.

20. Troubleshooting Guide

DAG does not appear in the UI
  • Confirm the file is inside the mounted dags folder.
  • Check import errors: docker compose exec airflow-scheduler airflow dags list-import-errors.
  • Check DAG Processor and Scheduler logs.
  • Ensure the Python module imports exist in the Airflow image.
  • Verify the DAG function is invoked.
Task remains queued
  • Check worker health and executor configuration.
  • Check pool slots and task queue.
  • Check DAG concurrency and global parallelism.
  • Check whether workers can access required images or dependencies.
Task fails with ModuleNotFoundError
  • The package is not installed inside the Airflow container.
  • Build a custom image using a Dockerfile and pinned requirements.
  • Keep Airflow at the same version while installing additional dependencies.
Windows path works on host but not inside container

Containers use Linux paths. A mounted host folder such as C:\AirflowLab\dags appears inside the container as /opt/airflow/dags. Use the container path in DAG code.

Connection to a service on the Windows host fails

Inside a container, localhost refers to that container. Use host.docker.internal when connecting to an appropriate host service, and ensure the host service accepts external/container connections.

Scheduler or API server is unhealthy
  • Run docker compose ps.
  • Inspect component logs.
  • Check Docker memory.
  • Check PostgreSQL and Redis health.
  • Use the Airflow health endpoint and scheduler heartbeat diagnostics.
Duplicate data after retry

The task is not idempotent. Write into a deterministic date partition, use merge/upsert logic, or delete and replace the run’s owned output before writing.

21. Best Practices and Anti-Patterns

Do

  • Keep DAG structure simple and readable.
  • Use fixed timezone-aware dates.
  • Design tasks for safe retries.
  • Pass paths and metadata through XCom.
  • Store large data externally.
  • Use provider hooks and operators.
  • Set retries, timeouts, and alerts intentionally.
  • Protect shared systems with pools.
  • Document ownership and support procedures.
  • Test before deployment.

Avoid

  • Network calls at DAG parse time.
  • Hard-coded credentials.
  • One enormous Python task for the entire pipeline.
  • Large DataFrames in XCom.
  • Blind append on every retry.
  • Unbounded parallelism.
  • Ignoring timezone and data interval semantics.
  • Using local worker disk as durable shared storage.
  • Production use of the learning Compose file.
  • Alerting without actionable context.

Code review checklist

  • Clear DAG and task names.
  • Owner/team tags.
  • Fixed start date.
  • Correct schedule and timezone.
  • Catchup decision documented.
  • Retries appropriate for failure type.
  • Execution timeout set.
  • Idempotent writes.
  • No secret in source.
  • No large XCom.
  • Pool for constrained system.
  • Failure alert contains support details.

24. Interview Questions and Answers

1. What problem does Airflow solve?

It orchestrates multi-step workflows by defining dependencies, schedules, retries, state, and observability as code.

2. What is the difference between a DAG and a task?

A DAG is the workflow blueprint; a task is one unit of work inside it.

3. What is the difference between a task and a task instance?

A task is a definition. A task instance is that definition for a particular DAG run and has a state, attempt, logs, and timing.

4. What does the Scheduler do?

It creates eligible DAG runs, evaluates dependencies and constraints, and sends runnable task instances to the Executor.

5. What does the Executor do?

It implements how task instances are dispatched and run, such as locally, on distributed workers, or in Kubernetes pods.

6. Why should Airflow tasks be idempotent?

Because failures, retries, reruns, and backfills are normal. Idempotency prevents duplicate or inconsistent output.

7. What is XCom and what should not be stored in it?

XCom carries small task-to-task metadata. Large datasets, DataFrames, and files should be stored externally and referenced by path or ID.

8. What is catchup?

Catchup creates scheduled DAG runs for historical intervals between a fixed start date and the current schedule.

9. What is backfill?

Backfill is intentional execution of historical logical intervals, often after code changes or missed processing.

10. Why use pools?

Pools limit parallel access to constrained services such as a small database, partner API, or licensed system.

11. Sensor poke mode versus reschedule mode?

Poke mode occupies a worker while sleeping. Reschedule mode releases the worker between checks. Deferrable operators can move waiting to the Triggerer.

12. Why avoid dynamic current time as start_date?

It continuously moves the scheduling boundary and makes schedule calculation unpredictable. Use a fixed timezone-aware date.

13. How do you troubleshoot a queued task?

Check executor and worker health, pool slots, queues, concurrency settings, priority, and available capacity.

14. How should credentials be managed?

Use Airflow Connections integrated with a secrets backend or secure environment mechanism. Never hard-code credentials in DAGs.

15. How do you handle heavy Spark processing?

Use Airflow to submit and monitor a Spark job on suitable compute. Do not run a huge Spark workload inside the Scheduler process.

16. Airflow versus Cron?

Cron is suitable for simple time triggers. Airflow adds dependency graphs, task-level state, retries, history, backfill, scaling, and central observability.

17. Airflow versus Kafka?

Kafka is an event streaming platform. Airflow is a workflow orchestrator. They frequently work together.

18. What is dynamic task mapping?

It creates task instances at runtime based on upstream data using mapping operations such as expand().

19. What is asset-aware scheduling?

It schedules downstream workflows based on updates to logical data assets instead of relying only on clock time.

20. What makes an Airflow deployment production ready?

Secure access, supported metadata database, backups, secrets, monitoring, remote logs, scalable execution, tested DAG delivery, health checks, and operational ownership.
