2. Messaging Basics

Messaging lets applications exchange data through an intermediary instead of directly depending on one another.

Synchronous

Checkout calls Inventory and waits. If Inventory is slow, Checkout also waits.

Asynchronous

Checkout publishes an event and continues. Inventory processes it independently.

Event: A record that something happened, such as “Order O-1001 was created.”

3. What is Pub/Sub?

Publish/subscribe is a messaging pattern in which publishers send messages to a topic and subscribers receive them through subscriptions.

  • Publisher does not need to know all receivers.
  • One topic can feed multiple independent subscriptions.
  • Subscribers process messages at their own pace.
Google Cloud Pub/Sub is a fully managed real-time messaging service. Google manages messaging servers, scaling and availability.
Pub/Sub programmatic access uses Google Cloud credentials such as gcloud credentials, Application Default Credentials or service identities—not a normal API key.

4. Why Use Pub/Sub?

Loose coupling

Publisher and subscriber can change independently.

Fan-out

One event can reach warehouse, analytics and notification systems.

Buffering

Messages can wait in a subscription while a consumer catches up.

Failure isolation

A failed subscriber does not require the publisher to stop.

Independent scale

Each application scales according to its workload.

Event-driven design

Services react to business events instead of constant polling.

5. Architecture

Important: Applications receive messages through subscriptions. The subscription owns delivery and acknowledgment state.

7. Topic vs Subscription

Topic

Publisher-facing named message stream.

  • Receives published events.
  • Can have many subscriptions.
  • Does not represent one consuming application.

Subscription

Subscriber-facing delivery stream.

  • Connected to one topic.
  • Tracks delivery and ACK state.
  • Can use pull or push.
AspectTopicSubscription
SidePublisherSubscriber
PurposeAccept/categoryDeliver/track
RelationshipOne-to-many subscriptionsBelongs to one topic

Create a subscription before publishing messages that it must receive. A new standard subscription normally receives later messages unless a separate retention/replay design is configured.

8. How It Works

  1. Publisher creates an event.
  2. Publisher sends it to the topic.
  3. Pub/Sub makes it available to attached subscriptions.
  4. Pull subscriber requests it, or Pub/Sub pushes it to an HTTPS endpoint.
  5. Subscriber processes the event.
  6. Subscriber acknowledges success.
  7. No ACK or failure can cause redelivery.
Acknowledging a message on one subscription does not acknowledge it on another subscription.

10. ACK, Retry and Redelivery

A message is successfully processed only when acknowledged.

ACK

Processing succeeded.

NACK/failure

Processing failed and delivery may retry.

Deadline expiry

No timely ACK, so redelivery may occur.

Design for duplicates: Store a processed message/event ID or enforce a unique business operation. ACK only after durable processing succeeds.

11. Kafka vs Google Cloud Pub/Sub

AspectApache KafkaGoogle Cloud Pub/Sub
ModelOpen-source distributed event-streaming platform.Fully managed Google Cloud messaging service.
StructureTopics divided into partitions.Topics connected to subscriptions.
InfrastructureBrokers store partition replicas.Broker infrastructure is managed and hidden.
ConsumersConsumer groups share partitions.A separate subscription commonly represents each independent workload.
ProgressOffsets per partition.Acknowledgment/delivery state per subscription.
DeliveryConsumers normally fetch.Pull or push delivery.
OrderingPer-partition ordering.Ordering keys when enabled; no user-managed Kafka-style partitions.
ScalingPlan partitions, brokers, replicas and storage.Managed service scaling without user brokers.
ReplayMove offsets over retained logs.Use retention, seek and snapshots where configured.
PortabilityRuns across clouds and on-premises.Native Google Cloud service.
Do not map Pub/Sub subscription to Kafka partition. Subscription is closer to an independent consumer workload. Kafka partition is an ordered data shard.

12. Which Should You Choose?

Choose Pub/Sub

  • Google Cloud-native systems
  • Minimal infrastructure management
  • Cloud Run/Dataflow/BigQuery integration
  • Push or managed pull delivery

Choose Kafka

  • Cross-cloud or on-premises portability
  • Explicit partition control
  • Kafka Streams/ecosystem requirements
  • Long-lived log and offset-centric replay

17. End-to-End Push Demo with Cloud Run

Training simplification: The first demo allows public access. Production push should use authenticated delivery with a dedicated service account and identity-token verification.

1. Create files

mkdir -p ~/pubsub-push-demo
cd ~/pubsub-push-demo

cat > main.py <<'PY'
import base64
import json
import os
from flask import Flask, request

app = Flask(__name__)

@app.get("/")
def health():
    return "Pub/Sub push receiver is running", 200

@app.post("/")
def receive():
    envelope = request.get_json(silent=True)
    if not envelope or "message" not in envelope:
        return "Invalid Pub/Sub envelope", 400

    message = envelope["message"]
    encoded = message.get("data", "")

    try:
        decoded = base64.b64decode(encoded).decode("utf-8") if encoded else ""
    except Exception:
        return "Invalid base64 data", 400

    try:
        event = json.loads(decoded) if decoded else {}
    except json.JSONDecodeError:
        event = {"rawText": decoded}

    record = {
        "messageId": message.get("messageId") or message.get("message_id"),
        "attributes": message.get("attributes", {}),
        "subscription": envelope.get("subscription"),
        "event": event,
    }
    print("PUSH_MESSAGE_RECEIVED " + json.dumps(record), flush=True)

    # 204 acknowledges successful push processing.
    return "", 204

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=int(os.environ.get("PORT", "8080")))
PY

18. Optional Python Pull Subscriber

1. Install library

mkdir -p ~/pubsub-python-demo
cd ~/pubsub-python-demo
python3 -m venv .venv
source .venv/bin/activate
pip install google-cloud-pubsub

2. Create subscriber.py

cat > subscriber.py <<'PY'
import os
from concurrent.futures import TimeoutError
from google.cloud import pubsub_v1

project_id = os.environ["PROJECT_ID"]
subscription_id = os.environ["WAREHOUSE_SUB"]

client = pubsub_v1.SubscriberClient()
path = client.subscription_path(project_id, subscription_id)

def callback(message):
    print("Data:", message.data.decode("utf-8"))
    print("Attributes:", dict(message.attributes))
    print("Message ID:", message.message_id)
    message.ack()

future = client.subscribe(path, callback=callback)
print(f"Listening on {path}. Press Ctrl+C to stop.")

with client:
    try:
        future.result(timeout=120)
    except TimeoutError:
        future.cancel()
        future.result()
    except KeyboardInterrupt:
        future.cancel()
PY

python subscriber.py

20. Troubleshooting

API disabled

Run gcloud services enable pubsub.googleapis.com. Enable Run, Build and Artifact Registry for the push lab.

PERMISSION_DENIED

Check gcloud auth list and gcloud config get-value project. Ask an administrator for required minimum IAM roles.

Pull returns no message

The subscription may have been created after publish, another client may have ACKed it, or you may be in the wrong project. Publish a fresh message and retry.

Push returns 403

The Cloud Run service requires authentication. For this lab redeploy with public access. For production configure authenticated push properly.

Unreadable push data

Decode the base64 string in message.data.

Repeated messages

The endpoint may return non-success, time out or crash before ACK. Check logs and use idempotent processing.

Python authentication failure

Cloud Shell normally needs no extra login. Locally run gcloud auth application-default login. Never hard-code service-account keys.

21. Best Practices

Events

  • Use business-oriented names.
  • Include event type, ID, timestamp and schema version.
  • Do not place secrets in messages.

Subscriptions

  • One subscription per independent workload.
  • Configure retry, retention and dead-letter handling.
  • Monitor backlog and oldest unacked message.

Subscribers

  • Make handlers idempotent.
  • ACK after durable success.
  • Use bounded concurrency and error classification.

Security

  • Use least-privilege IAM.
  • Prefer service identities.
  • Use authenticated push in production.

23. Interview Questions and Answers

1. What is Pub/Sub messaging?

A pattern where publishers send messages to topics and subscribers receive them through independent subscriptions.

2. What is Google Cloud Pub/Sub?

A fully managed Google Cloud real-time asynchronous messaging service.

3. Topic vs subscription?

Topic accepts publisher messages. Subscription delivers and tracks messages for a subscriber workload.

4. Can one topic have multiple subscriptions?

Yes. Each receives its own eligible copy.

5. Does one subscription ACK affect another?

No. ACK state is independent.

6. What is pull delivery?

The subscriber requests messages.

7. What is push delivery?

Pub/Sub sends HTTPS requests to the configured endpoint.

8. How does push ACK work?

The endpoint returns a supported HTTP success response, commonly 200 or 204.

9. Why base64 in push?

Message bytes are represented safely inside the default wrapped JSON body.

10. What causes redelivery?

No ACK, NACK, processing failure or acknowledgment deadline expiry.

11. Why idempotency?

A message can be delivered more than once.

12. Kafka vs Pub/Sub?

Kafka exposes brokers, partitions and offsets. Pub/Sub hides broker infrastructure and uses managed topics, subscriptions and ACK state.

13. Is a subscription a Kafka partition?

No. A subscription is an independent delivery stream; a Kafka partition is an ordered shard.

14. Closest Pub/Sub concept to Kafka consumer group?

A separate subscription is often closest for one independent consuming application, but the architectures are not identical.

15. When should ACK happen?

After successful durable processing.

16. Does Pub/Sub use API keys?

No. Use Google Cloud authentication such as ADC or service identities.

17. What is a dead-letter topic?

An optional destination for repeatedly undeliverable messages.

18. When choose pull?

For workers needing direct flow and concurrency control.

19. When choose push?

For reachable HTTPS services, webhooks and serverless handlers.

20. How to prevent duplicate orders?

Use idempotency keys, unique constraints or a processed-events table.
