1. Introduction, Purpose and Learning Outcomes

A Spark cluster manager allocates CPU and memory resources to Spark applications and launches executors on worker machines. Amazon EMR is the managed AWS platform that provisions and operates big-data infrastructure. On an EMR on EC2 Spark cluster, YARN normally performs the cluster-manager role.

Most important distinction Amazon EMR is the managed platform. YARN is the Spark cluster manager inside the EMR on EC2 cluster.

Understand

Driver, executor, YARN ResourceManager, NodeManager, primary, core and task nodes.

Create

Implement

A PySpark weather data-engineering pipeline using an open AWS S3 dataset.

Operate

Submit, monitor, scale, troubleshoot and terminate the cluster safely.

Purpose

  • Remove the burden of manually installing Hadoop, Spark, YARN and related services on many EC2 machines.
  • Scale batch, SQL, streaming, data-lake and machine-learning workloads.
  • Read data directly from Amazon S3 and write reusable Parquet outputs.
  • Create transient clusters for scheduled workloads or long-running clusters for continuous processing.

2. What Is a Spark Cluster Manager?

When you call spark-submit, Spark needs machines on which to run the driver and executors. The cluster manager is the resource-allocation layer between the Spark application and the available compute infrastructure.

Main responsibilities

Resource allocation

Assigns memory and CPU containers/pods/processes to an application.

Executor lifecycle

Starts, monitors and removes executor processes.

Multi-tenancy

Shares cluster capacity among multiple applications and queues.

Failure handling

Reschedules failed containers and reports application state.

Section 3

3. Amazon EMR Architecture and Node Types

Amazon EMR on EC2 creates a managed cluster from EC2 instances. The three logical node types are primary, core and task.

NodeMain responsibilityData-engineering guidance
PrimaryCoordinates the cluster and runs management daemons.Use On-Demand for stability. Production HA can use three primary nodes where supported.
CoreRuns compute and HDFS storage.Use stable capacity because removing a core node can affect HDFS blocks and application masters.
TaskAdds compute without HDFS DataNode storage.Good candidate for elastic and Spot capacity for fault-tolerant workloads.

Spark execution inside the cluster

  1. A Spark step is submitted to EMR.
  2. spark-submit submits the application to YARN.
  3. The driver creates a logical plan and DAG.
  4. YARN allocates executor containers on core/task nodes.
  5. Executors read S3 data through EMRFS, process partitions and shuffle when required.
  6. Executors write Parquet/CSV output back to S3.
  7. Logs and application status are available through EMR, YARN and Spark interfaces.

EMR deployment choices

DeploymentInfrastructure controlWhen to choose
EMR on EC2Highest cluster-level controlCustom networking, long-running clusters, specific instance types, HDFS or custom software.
EMR ServerlessNo cluster managementJob-oriented Spark/Hive when you do not want to plan nodes.
EMR on EKSKubernetes-nativeOrganizations already standardised on EKS.

5. Prerequisites and Cluster Planning

AWS resources required

  • An AWS account and an IAM identity allowed to use EMR, EC2, S3 and iam:PassRole.
  • A project S3 bucket for application code, output and logs.

6. Create an EMR Spark Cluster — Console and CLI

Console procedure

  1. Open the AWS console and select the intended region.
  2. Open Amazon EMR → EMR on EC2 → Clusters → Create cluster.
  3. Enter the cluster name weather-data-engineering-emr.
  4. Select the approved EMR release; this lab references emr-7.13.0.
  5. Select Hadoop, Spark and Hive.
  6. Select Instance groups.
  7. Choose one primary and two core instances.
  8. Select the VPC and subnet.
  9. Configure the EC2 key pair only when SSH is required.
  10. Set the S3 log URI.
  11. Enable an idle auto-termination policy.
  12. Select the EMR service role and EC2 instance profile.
  13. Add project/environment tags.
  14. Choose Create cluster and wait for WAITING.

AWS CLI procedure

Copy config/env.example to config/env.sh, replace placeholders, and run the supplied script.

#!/usr/bin/env bash
set -euo pipefail

source "${1:-config/env.sh}"

if [[ "$PROJECT_BUCKET" == replace-* ]]; then
  echo "Update config/env.sh before running."
  exit 1
fi

EC2_ATTRIBUTES="InstanceProfile=${EMR_EC2_INSTANCE_PROFILE},SubnetId=${SUBNET_ID}"
if [[ -n "${KEY_PAIR_NAME:-}" ]]; then
  EC2_ATTRIBUTES="${EC2_ATTRIBUTES},KeyName=${KEY_PAIR_NAME}"
fi

CLUSTER_ID=$(aws emr create-cluster \
  --region "$AWS_REGION" \
  --name "weather-data-engineering-emr" \
  --release-label "$EMR_RELEASE" \
  --applications Name=Hadoop Name=Spark Name=Hive \
  --service-role "$EMR_SERVICE_ROLE" \
  --ec2-attributes "$EC2_ATTRIBUTES" \
  --instance-groups \
    "InstanceGroupType=MASTER,Name=Primary,InstanceType=${PRIMARY_INSTANCE_TYPE},InstanceCount=1,Market=ON_DEMAND" \
    "InstanceGroupType=CORE,Name=Core,InstanceType=${CORE_INSTANCE_TYPE},InstanceCount=${CORE_INSTANCE_COUNT},Market=ON_DEMAND" \
  --log-uri "s3://${PROJECT_BUCKET}/emr-logs/" \
  --auto-termination-policy "IdleTimeout=${IDLE_TIMEOUT_SECONDS}" \
  --tags Project=WeatherEMRDemo Environment=Training \
  --query "ClusterId" \
  --output text)

echo "$CLUSTER_ID" | tee .cluster-id
echo "Cluster created: $CLUSTER_ID"
echo "Wait until state is WAITING before submitting the job."

Applications

Hadoop, Spark and Hive.

Instances

One primary and two core nodes.

Logging

Cluster and step logs archived under the project S3 bucket.

Cleanup

Idle auto-termination after the configured timeout.

Cost warning: EMR on EC2 charges include EMR and EC2 usage, with possible additional S3, EBS, transfer and logging costs. Terminate training clusters promptly.

A climate-risk data-engineering team receives global daily weather observations. Analysts require cleaned Celsius temperatures, precipitation values, station/year summaries and quality metrics in S3.

Open dataset

The reference application reads the NOAA Global Surface Summary of Day dataset from the Registry of Open Data on AWS:

The lab uses the small historical prefix:

Section 8

8. PySpark Application — Step-by-Step Explanation

Complete application

"""
NOAA GSOD weather analytics reference application for Amazon EMR.

The default input uses the public NOAA Global Surface Summary of Day
bucket in the Registry of Open Data on AWS. For a low-cost lab, the
example uses the 1929 prefix, which is much smaller than modern years.

EMR example:
  spark-submit weather_emr_pipeline.py \
    --input s3://noaa-gsod-pds/1929/ \
    --output s3://YOUR-BUCKET/emr-weather-demo/output/run-001/

Local smoke test:
  spark-submit weather_emr_pipeline.py \
    --input file:///absolute/path/sample_weather_gsod_compatible.csv \
    --output file:///absolute/path/output/
"""

from __future__ import annotations

import argparse
from typing import Optional

from pyspark.sql import DataFrame, SparkSession
from pyspark.sql import functions as F
from pyspark.sql.types import DoubleType


def parse_args() -> argparse.Namespace:
    parser = argparse.ArgumentParser(
        description="Clean and aggregate NOAA GSOD weather data."
    )
    parser.add_argument(
        "--input",
        default="s3://noaa-gsod-pds/1929/",
        help="Input CSV path or prefix.",
    )
    parser.add_argument(
        "--output",
        required=True,
        help="Output root, normally an S3 URI.",
    )
    parser.add_argument(
        "--year",
        type=int,
        default=None,
        help="Optional year filter after parsing DATE.",
    )
    parser.add_argument(
        "--shuffle-partitions",
        type=int,
        default=24,
        help="Spark SQL shuffle partition count for this job.",
    )
    return parser.parse_args()


def valid_numeric(column: str, missing_value: float) -> F.Column:
    """Cast a GSOD numeric field and convert its sentinel to NULL."""
    value = F.col(column).cast(DoubleType())
    return F.when(value == F.lit(missing_value), F.lit(None)).otherwise(value)


def fahrenheit_to_celsius(column: F.Column) -> F.Column:
    return F.round((column - F.lit(32.0)) * F.lit(5.0 / 9.0), 2)


def build_clean_daily(raw: DataFrame, year: Optional[int]) -> DataFrame:
    cleaned = (
        raw
        .withColumn("observation_date", F.to_date("DATE"))
        .withColumn("year", F.year("observation_date"))
        .withColumn("temp_f", valid_numeric("TEMP", 9999.9))
        .withColumn("max_temp_f", valid_numeric("MAX", 9999.9))
        .withColumn("min_temp_f", valid_numeric("MIN", 9999.9))
        .withColumn("precipitation_in", valid_numeric("PRCP", 99.99))
        .withColumn("wind_speed_knots", valid_numeric("WDSP", 999.9))
        .withColumn("temp_c", fahrenheit_to_celsius(F.col("temp_f")))
        .withColumn(
            "max_temp_c",
            fahrenheit_to_celsius(F.col("max_temp_f")),
        )
        .withColumn(
            "min_temp_c",
            fahrenheit_to_celsius(F.col("min_temp_f")),
        )
        .select(
            F.col("STATION").alias("station_id"),
            F.trim(F.col("NAME")).alias("station_name"),
            "observation_date",
            "year",
            F.col("LATITUDE").cast("double").alias("latitude"),
            F.col("LONGITUDE").cast("double").alias("longitude"),
            "temp_c",
            "max_temp_c",
            "min_temp_c",
            "precipitation_in",
            "wind_speed_knots",
            F.col("FRSHTT").alias("weather_event_flags"),
        )
        .filter(
            F.col("station_id").isNotNull()
            & F.col("observation_date").isNotNull()
        )
    )

    if year is not None:
        cleaned = cleaned.filter(F.col("year") == F.lit(year))

    return cleaned


def build_station_summary(cleaned: DataFrame) -> DataFrame:
    return (
        cleaned
        .groupBy("year", "station_id", "station_name")
        .agg(
            F.count("*").alias("observation_days"),
            F.round(F.avg("temp_c"), 2).alias("avg_temp_c"),
            F.round(F.max("max_temp_c"), 2).alias("highest_temp_c"),
            F.round(F.min("min_temp_c"), 2).alias("lowest_temp_c"),
            F.round(F.sum("precipitation_in"), 2).alias(
                "total_precipitation_in"
            ),
            F.round(F.avg("wind_speed_knots"), 2).alias(
                "avg_wind_speed_knots"
            ),
        )
        .orderBy("year", F.desc("avg_temp_c"))
    )


def build_quality_metrics(raw: DataFrame, cleaned: DataFrame) -> DataFrame:
    raw_count = raw.count()
    cleaned_count = cleaned.count()
    metrics = [
        ("raw_rows", raw_count),
        ("cleaned_rows", cleaned_count),
        ("rejected_or_unusable_rows", raw_count - cleaned_count),
        (
            "rows_with_missing_mean_temperature",
            cleaned.filter(F.col("temp_c").isNull()).count(),
        ),
        (
            "rows_with_missing_precipitation",
            cleaned.filter(F.col("precipitation_in").isNull()).count(),
        ),
    ]
    return cleaned.sparkSession.createDataFrame(
        metrics,
        ["metric_name", "metric_value"],
    )


def main() -> None:
    args = parse_args()

    spark = (
        SparkSession.builder
        .appName("NOAA-GSOD-Weather-Analytics")
        .getOrCreate()
    )
    spark.sparkContext.setLogLevel("WARN")
    spark.conf.set(
        "spark.sql.shuffle.partitions",
        str(args.shuffle_partitions),
    )

    try:
        raw = (
            spark.read
            .option("header", True)
            .option("mode", "PERMISSIVE")
            .csv(args.input)
        )

        cleaned = build_clean_daily(raw, args.year).cache()
        station_summary = build_station_summary(cleaned)
        quality_metrics = build_quality_metrics(raw, cleaned)

        cleaned.write.mode("overwrite").partitionBy("year").parquet(
            f"{args.output.rstrip('/')}/cleaned_daily"
        )
        station_summary.write.mode("overwrite").parquet(
            f"{args.output.rstrip('/')}/station_summary"
        )
        station_summary.write.mode("overwrite").option(
            "header", True
        ).csv(f"{args.output.rstrip('/')}/station_summary_csv")
        quality_metrics.write.mode("overwrite").option(
            "header", True
        ).csv(f"{args.output.rstrip('/')}/quality_metrics")

        print("Input:", args.input)
        print("Output:", args.output)
        print("Cleaned rows:", cleaned.count())
        print("Station summary preview:")
        station_summary.show(20, truncate=False)
        print("Quality metrics:")
        quality_metrics.show(truncate=False)
    finally:
        try:
            cleaned.unpersist()
        except UnboundLocalError:
            pass
        spark.stop()


if __name__ == "__main__":
    main()

How each part works

1. Parse arguments

Allows the same program to use public S3 input, project S3 output or local test files.

2. Create SparkSession

On EMR, Spark uses YARN without setting a local master.

3. Read CSV

Spark reads many S3 objects in parallel.

4. Clean data

Sentinel values become nulls, dates are parsed and Fahrenheit is converted to Celsius.

5. Cache

The cleaned DataFrame is reused by summary and quality actions.

6. Aggregate

Station/year grouping creates observation counts, average temperature, extremes, precipitation and wind summaries.

7. Write

Clean data and aggregates are written to durable S3 prefixes.

8. Unpersist and stop

Cached memory is released and the application ends cleanly.

Transformation vs action examples

OperationTypeExecution impact
withColumn, select, filterTransformationBuilds a lazy logical plan.
groupBy().agg()Transformation with shuffle when executedRecords move by aggregation keys.
count()ActionTriggers a Spark job.
write.parquet()ActionExecutes lineage and writes S3 objects.
show()ActionReturns a limited result for display.

Why Parquet?

  • Columnar storage reduces scan volume for analytical queries.
  • Supports schema and efficient compression.
  • Works well with Athena, Glue, Redshift Spectrum and Spark.
  • Partitioning by year allows partition pruning.

9. Submit, Monitor and Validate the Spark Job

Upload application and add an EMR step

#!/usr/bin/env bash
set -euo pipefail

source "${1:-config/env.sh}"
CLUSTER_ID="${CLUSTER_ID:-$(cat .cluster-id)}"
RUN_ID="${RUN_ID:-run-$(date +%Y%m%d-%H%M%S)}"
CODE_URI="s3://${PROJECT_BUCKET}/emr-weather-demo/code/weather_emr_pipeline.py"
OUTPUT_URI="s3://${PROJECT_BUCKET}/emr-weather-demo/output/${RUN_ID}/"

aws s3 cp app/weather_emr_pipeline.py "$CODE_URI" --region "$AWS_REGION"

STEP_ID=$(aws emr add-steps \
  --region "$AWS_REGION" \
  --cluster-id "$CLUSTER_ID" \
  --steps "Type=CUSTOM_JAR,Name=NOAA-Weather-Analytics,ActionOnFailure=CONTINUE,Jar=command-runner.jar,Args=[spark-submit,--deploy-mode,cluster,${CODE_URI},--input,s3://noaa-gsod-pds/1929/,--output,${OUTPUT_URI},--year,1929,--shuffle-partitions,24]" \
  --query "StepIds[0]" \
  --output text)

echo "$STEP_ID" | tee .step-id
echo "$OUTPUT_URI" | tee .output-uri
echo "Step submitted: $STEP_ID"
echo "Output: $OUTPUT_URI"

10. Scaling, Performance and Production Design

Scale-up choices

ProblemPossible responseTrade-off
CPU-bound tasksAdd task nodes or larger compute-optimised instances.Higher cost; verify parallelism.
Memory pressureUse memory-optimised nodes or reduce cached/shuffle data.Larger nodes are more expensive.
Long shuffleFilter/project earlier, tune partitions, reduce skew.Requires workload analysis, not only more machines.
Uneven tasksInvestigate skewed keys and partition sizes.May require salting or design changes.
Temporary backfillAdd Spot task nodes and managed scaling.Jobs must tolerate interruptions.

Instance strategy

  • Keep primary nodes stable, normally On-Demand.
  • Use reliable core capacity because it can hold HDFS blocks and critical application processes.
  • Use task nodes for elastic compute and consider Spot for retry-safe workloads.
  • Use instance fleets when multiple instance types and purchasing options improve capacity availability.

Managed scaling

EMR managed scaling can add or remove core/task capacity according to workload demand and configured limits. Test decommissioning behaviour for long-running applications.

Spark performance checklist

File sizing

Avoid millions of tiny files. Compact outputs into useful file sizes.

Partition pruning

Partition data by fields commonly used in filters, but avoid excessive cardinality.

Projection

Select only required columns before expensive operations.

Shuffle tuning

Set shuffle partitions based on data volume and available cores.

Skew handling

Identify dominant keys, salt or use adaptive strategies.

Storage format

Prefer Parquet or a supported open table format for analytics.

Transient vs long-running cluster

PatternAdvantagesBest use
TransientClean environment, no idle cluster, workflow-specific sizingScheduled batch jobs and backfills
Long-runningFast repeated submissions and interactive accessShared development, continuous/streaming workloads
Performance memory aid: Reduce data early → balance partitions → avoid skew → write columnar files → measure in Spark UI.

  • Use private subnets and controlled egress in production.
  • Use security configurations for encryption and authentication requirements.
  • Encrypt S3 buckets, logs and EBS volumes as required.
  • Use Lake Formation/Glue governance when appropriate.
  • Separate development, test and production accounts or environments.
  • Do not put secrets directly in scripts; use approved secret-management mechanisms.

SSH guidance

Never: Allow TCP port 22 from 0.0.0.0/0.

When SSH is necessary, authorise only a trusted IP range. EMR's default primary security group does not need public SSH for jobs submitted as steps.

Best practices

Make jobs idempotent

Use versioned run paths or controlled overwrite so retries do not corrupt results.

Separate compute and storage

Keep durable data in S3 so clusters can be disposable.

Pin releases

Test and approve EMR/Spark versions before production updates.

Log every run

Capture cluster ID, step ID, code version, input and output.

Validate before publish

Check counts, nulls, duplicates, ranges and schema.

Use orchestration

Coordinate production EMR jobs with approved workflow services.

Edge cases to teach

  • The input year can contain many small station files, producing small-file overhead.
  • Weather sentinel values must not be treated as real temperatures.
  • Schema can evolve; select and cast explicitly.
  • Cross-region data reads can increase latency and cost.
  • Spot interruption should not destroy durable output or require a full manual restart.
  • HDFS data disappears when a transient cluster is terminated.

Operational runbook

  1. Record cluster ID and step ID.
  2. Check EMR step status.
  3. Open failed-step logs.
  4. Find the first real exception, not only the final wrapper error.
  5. Classify as permissions, data, code, resources or infrastructure.
  6. Fix the root cause.
  7. Write to a new run prefix or use a controlled overwrite.
  8. Validate output and terminate resources.

Interview questions and answers

1. What is a Spark cluster manager?

It allocates cluster resources and launches Spark executors. Examples are YARN, Kubernetes and Spark Standalone.

2. Is Amazon EMR a Spark cluster manager?

No. It is a managed platform. Spark on EMR on EC2 usually uses YARN as its cluster manager.

3. What does the EMR primary node do?

It coordinates cluster services and normally runs management daemons such as YARN ResourceManager and HDFS NameNode.

4. Core node vs task node?

Both can run compute. Core nodes also run HDFS DataNode storage; task nodes add compute without HDFS DataNode storage.

5. Why store durable data in S3?

S3 is independent of the transient cluster lifecycle, allowing clusters to be terminated and recreated.

6. What is an EMR step?

A unit of work submitted to a cluster, such as a Spark application launched through spark-submit.

7. What is cluster deploy mode?

The Spark driver runs inside a cluster-managed container, so it is not dependent on the submitting shell session.

8. Why use task nodes for Spot?

They add compute without HDFS storage and can suit fault-tolerant retryable work, reducing the impact of interruption.

9. Why can groupBy cause expensive work?

Records with the same key must move across the network, creating a shuffle and potential skew.

10. How do you troubleshoot a failed Spark step?

Check the step status reason, driver logs, YARN container logs and Spark stages, then identify permissions, data, code or resource problems.

11. Why use Parquet?

It is columnar, compressed and schema-aware, reducing analytical scan cost.

12. What is EMRFS?

It is the EMR file-system integration that lets Hadoop/Spark access Amazon S3 directly.

13. Transient vs long-running cluster?

Transient clusters suit scheduled batch jobs and minimise idle time; long-running clusters suit shared interactive or continuous workloads.

14. What does managed scaling do?

It adjusts core/task capacity within configured limits according to workload demand.

15. Why avoid SSH from 0.0.0.0/0?

It exposes the primary node to internet-wide connection attempts and is an unsafe security practice.

16. How do you control EMR cost?

Right-size, use auto-termination, terminate explicitly, consider Spot task nodes, tag resources and measure jobs.

17. What happens to HDFS when the cluster terminates?

Cluster-tied HDFS data is lost; durable outputs should be copied to S3.

18. What causes Spark data skew?

A few keys or files create disproportionately large partitions, causing long-running straggler tasks.

19. DataFrame or RDD on EMR?

Use DataFrames/Spark SQL for most structured engineering. Use RDDs for special low-level custom processing.

20. How can EMR jobs be orchestrated?

Use EMR Steps with approved workflow services such as Step Functions, Airflow/MWAA or scheduled automation.

Glossary and conclusion

Cluster manager

Allocates resources to Spark applications.

EMR step

A submitted unit of cluster work.

EMRFS

EMR integration for accessing S3.

Shuffle

Network redistribution of records between partitions.

Transient cluster

A cluster created for a workload and terminated afterward.

Task node

Compute-only EMR node without HDFS DataNode storage.

Final conclusion: EMR manages infrastructure, YARN manages Spark resources, Spark transforms data, and S3 provides durable data-lake storage.
