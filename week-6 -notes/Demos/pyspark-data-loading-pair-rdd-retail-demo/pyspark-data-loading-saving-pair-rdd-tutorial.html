1. What Is Data Loading?

Data loading is the process of bringing data from a source into Spark so that it can be divided into partitions and processed by distributed tasks. The source can be a local file, HDFS, S3, DBFS, a Python collection, a Hadoop input format, or a DataFrame in classic Spark.

Source

CSV, log, JSON text, HDFS, S3, database or collection.

Reader

parallelize, textFile, wholeTextFiles and others.

Partitions

Spark distributes input records across tasks.

Lineage

Spark remembers how the RDD was created for recomputation.

RDD loading and saving options available with Spark Classic architecture.

2. Why Do We Load Data?

  • To convert external information into Spark partitions.
  • To process datasets larger than Driver memory.
  • To create a repeatable ETL pipeline.
  • To validate source records before business calculations.
  • To integrate data from several systems using common keys.
  • To save cleaned and report-ready outputs for downstream users.
Without controlled loadingWith controlled loading
Manual local loopsDistributed partition processing
No validation layerClean and quarantine outputs
Hidden format assumptionsExplicit parsing and data contracts
Hard to reproduceRepeatable pipeline and output paths
Industry principle: Loading is not only opening a file. It includes source identification, path access, format parsing, partition planning, schema or type conversion, quality checks and lineage.

Path rule: a local file path must be available to every Spark worker. Local mode uses one machine, while clusters normally use distributed storage.

7. Key–Value Pair RDD

A Pair RDD contains elements shaped as (key, value). The key controls grouping, aggregation, partitioning and joins. The value contains the measures or record associated with that key.

The category key brings matching sales records and master records together.

sales = [
    ("Electronics", 47500.0),
    ("Grocery", 1200.0),
    ("Fashion", 4860.0),
    ("Electronics", 57040.0),
]

sales_pair_rdd = sc.parallelize(sales, 3)

category_totals = sales_pair_rdd.reduceByKey(
    lambda left, right: left + right
)

print(category_totals.collect())

Pair-RDD operations

OperationUse
reduceByKeySum or combine values for every key.
aggregateByKeyCalculate several metrics with custom accumulator.
groupByKeyKeep all original values; avoid for simple sums.
joinMatch two Pair RDDs using the key.
sortByKeySort by key.
lookupReturn values for one key.
countByKeySmall Driver-side key count dictionary.
partitionByControl key placement across partitions.

9. Parse, Validate, Clean and Quarantine

classified = (
    raw_orders
    .filter(lambda line: line != header)
    .mapPartitions(parse_order_partition)
    .map(classify_order)
    .cache()
)

input_count = classified.count()

clean_orders = (
    classified
    .filter(lambda item: item["valid"])
    .map(lambda item: item["row"])
    .cache()
)

rejected_orders = classified.filter(
    lambda item: not item["valid"]
)

Why this design?

  • mapPartitions creates one CSV reader per partition.
  • classify_order returns both valid records and rejection reasons.
  • cache is used because classified and clean RDDs support several later actions.
  • count materialises all cached partitions once.
  • Rejected data is retained instead of silently discarded.

10. Pair-RDD Aggregation and Master Join

category_metrics = completed_orders.map(
    lambda row: (
        row["category"],
        (1, row["quantity"], row["net_amount"]),
    )
)

def add_metric(left, right):
    return (
        left[0] + right[0],
        left[1] + right[1],
        left[2] + right[2],
    )

category_summary = category_metrics.aggregateByKey(
    (0, 0, 0.0),
    add_metric,
    add_metric,
)

The zero value means no orders, no units and no revenue. The sequence function adds a record inside a partition. The combine function merges partial category totals across partitions.

12. Databricks Steps, Best Practices and Troubleshooting

Legacy/classic RDD notebook

  1. Import Retail_Data_Loading_Pair_RDD_Legacy_Classic.dbc.
  2. Attach classic or Dedicated compute.
  3. Run all cells.
  4. The notebook creates source CSVs under legacy dbfs:/FileStore.
  5. It saves clean, rejected, report and SequenceFile directories.

Current Free Edition

  1. Import Retail_Data_Loading_Free_Edition_DataFrame_Alternative.dbc.
  2. Use the provided serverless compute.
  3. The notebook creates a Unity Catalog Volume.
  4. It loads CSV using spark.read, groups, joins and saves managed tables.
  5. It never calls spark.sparkContext or an RDD API.
ProblemCauseFix
RDD API unsupportedServerless or standard Spark Connect computeUse classic/Dedicated compute or the DataFrame alternative.
JAVA_GATEWAY_EXITEDJava missing or wrong environmentInstall Java 17+ and verify JAVA_HOME.
Output path existssaveAsTextFile does not overwriteDelete or version the directory.
Wrong CSV columnsQuoted comma parsed using splitUse csv.reader.

Industry practices: retain rejected records, reconcile counts, use idempotent output paths, validate master keys, use map-side aggregation, preserve raw inputs and avoid one-partition output for large data.
