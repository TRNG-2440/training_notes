Section 1

What is Dataproc?

Dataproc is Google Cloud’s managed way to provision and operate Apache Spark, Hadoop, Hive and related open-source data tools on Compute Engine virtual machines. Google automates cluster creation and service configuration; your team controls the data, code, IAM, network, machine sizing, job settings and lifecycle.

Without Dataproc

Create VMs, install Java/Hadoop/Spark, configure YARN/HDFS, integrate logging, patch services and repair failures.

With Dataproc

Create a managed cluster through Console, API or gcloud, submit jobs, inspect results, resize and delete.

Common workloads

Batch ETL, Spark SQL, Hadoop migration, feature engineering, Hive processing and data-lake transformation.

TechnologyRole

YARNResource manager that allocates CPU and memory containers.
HDFSCluster-local distributed filesystem on primary-worker disks.

D-P-O: Durable data → Processing cluster → Output to durable storage.

Master node

The master runs cluster-control services. YARN ResourceManager chooses where containers run; HDFS NameNode maintains filesystem metadata; the job/Spark driver builds the DAG and coordinates executors.

Primary workers

Primary workers run YARN NodeManager, HDFS DataNode and Spark executors. They provide compute plus HDFS capacity.

Secondary workers

Secondary workers are optional compute-only capacity and do not store HDFS data. They are well suited to elastic, retryable executor work and are commonly Spot/preemptible.

Staging and temp buckets

Dataproc uses Cloud Storage to stage job resources and temporary/history artifacts. The cluster VM service account needs access.

Best practice: Keep durable source and result data outside the cluster. HDFS and VM disks disappear with the cluster.

Section 5

Storage, IAM, Network and Web UIs

Cloud Storage connector

Spark and Hadoop jobs use gs:// paths directly through the connector included with managed cluster images.

VM service account

The cluster’s VMs use this identity for bucket, logging and other Google API access. Grant least privilege.

VPC and subnet

VMs must communicate internally and reach required Google APIs. Private designs commonly use Private Google Access.

Component Gateway

Provides IAM-controlled access to supported YARN, Spark History and component web UIs.

Section 9

Understand the PySpark ETL

Read with an explicit schema

Read CSV
raw = (
    spark.read.option("header", True)
    .option("mode", "PERMISSIVE")
    .schema(schema)
    .csv(args.input)
    .withColumn("order_date", F.to_date("order_date", "yyyy-MM-dd"))
)

Validate rows

Quality condition
valid = (
    F.col("order_id").isNotNull()
    & (F.trim("order_id") != "")
    & F.col("order_date").isNotNull()
    & (F.col("quantity") > 0)
    & (F.col("unit_price") > 0)
    & (F.upper("payment_status") == "PAID")
)

Deduplicate and calculate revenue

Clean DataFrame
clean = (
    raw.filter(valid)
    .dropDuplicates(["order_id"])
    .withColumn("revenue", F.round(F.col("quantity") * F.col("unit_price"), 2))
)

Aggregate

Wide transformation
summary = clean.groupBy("order_date", "state", "category").agg(
    F.countDistinct("order_id").alias("order_count"),
    F.sum("quantity").alias("units_sold"),
    F.round(F.sum("revenue"), 2).alias("total_revenue")
)
Why distributed? Executors filter and calculate locally. groupBy causes shuffle so records with the same keys arrive at the same aggregation tasks.

Section 11

Autoscaling, Security, Performance and Cost

Optional autoscaling

Import and attach policy
bash commands/07_optional_autoscaling.sh

The included policy keeps 2–4 primary workers and permits 0–6 secondary workers. Autoscaling changes worker count, not machine type.

Security checklist

Performance guidelines

  • Prefer Parquet for repeated analytics.
  • Use explicit schemas and early filtering.
  • Avoid large collect() operations.
  • Avoid coalesce(1) for large production output.
  • Control partition count and watch skew.
  • Co-locate cluster and bucket appropriately.
  • Use secondary workers for elastic retryable compute.

Cleanup

Delete compute
bash commands/06_cleanup.sh
Cost habit: create compute for the job, persist output externally, then delete compute. Idle deletion is only a backup.
Section 12

Troubleshooting

Check Dataproc/Compute/network permissions and iam.serviceAccounts.actAs. Confirm the VM account has roles/dataproc.worker.
Grant the VM service account the required bucket role and verify input, staging and temp paths.
Use Auto Zone, another machine family/region, smaller capacity or flexible VM types.
It is waiting for resources. Inspect memory, vCores, executor size, queues, concurrent jobs and autoscaling.
Spark retries tasks. Ensure work is retry-safe and do not depend on durable data on secondary workers.
Inspect driver/executor logs, skew, collect operations, caching and shuffle spill before increasing machines.
Confirm the cluster was created with the gateway, your IAM permits access and the component UI is supported.
Delete the cluster, inspect Compute Engine VMs/disks and review Billing by service and labels.
Diagnostics
gcloud dataproc clusters list --region="$REGION"
gcloud dataproc jobs list --region="$REGION"
gcloud dataproc clusters describe "$CLUSTER_NAME" --region="$REGION"
gcloud dataproc clusters diagnose "$CLUSTER_NAME" --region="$REGION"
