1. Introduction and Learning Outcomes

Spark tasks run in worker processes. Normal Python variables referenced by a task function are serialized as copies; worker updates do not automatically modify the Driver variable. Spark provides two shared-variable types: Broadcast Variables and Accumulators.

Broadcast sends read-only reference data outward; accumulators merge additive diagnostic updates back to the Driver.

Broadcast

Small read-only lookup shared with tasks.

Accumulator

Add-only task updates read by Driver.

Use Case

Retail enrichment plus data-quality counters.

2. Why a Normal Python Variable Does Not Work

driver_counter = 0

def increment_on_worker(_):
    global driver_counter
    driver_counter += 1

sc.parallelize(range(1, 11), 4).foreach(
    increment_on_worker
)

print(driver_counter)
# Driver value normally stays 0
LocationBehaviour
DriverCreates the original variable and submits tasks.
WorkerDeserializes a copy and updates only that process.
Driver after jobStill owns the original value.
Correct mental model: tasks do not share one mutable Python memory space.

4. Broadcast Variables

A small lookup is cached for task access through broadcast.value.

product_master = {{
    "P100": {{"category": "Electronics"}},
    "P200": {{"category": "Grocery"}},
}}

product_broadcast = sc.broadcast(
    product_master
)

enriched = orders_rdd.map(
    lambda order: {{
        **order,
        **product_broadcast.value.get(
            order["product_id"],
            {{"category": "UNKNOWN"}},
        ),
    }}
)

product_broadcast.unpersist()

Lifecycle

  1. Create on Driver.
  2. Broadcast once.
  3. Tasks access .value.
  4. unpersist() removes executor copies and permits later reuse.
  5. destroy() removes data and metadata permanently.

5. Numeric Accumulators

Tasks add values; only the Driver reads the merged result after an action.

invalid_records = sc.accumulator(0)

def validate(order):
    valid = (
        bool(order["city"])
        and order["quantity"] > 0
        and 0 <= order["discount_pct"] <= 100
    )

    if not valid:
        invalid_records.add(1)

    return valid

valid_orders = orders_rdd.filter(
    validate
).cache()

valid_count = valid_orders.count()

print(valid_count)
print(invalid_records.value)
  • Transformations are lazy, so updates occur only when an action runs.
  • Tasks should not depend on reading accumulator values.
  • Repeated uncached actions can repeat updates.
  • Use accumulators for diagnostics, not billing or financial truth.

6. Custom Accumulator Types

AccumulatorParam defines the zero value and the associative combination rule for a custom type.

from pyspark import AccumulatorParam

class DictAccumulatorParam(AccumulatorParam):
    def zero(self, value):
        return {{key: 0 for key in value}}

    def addInPlace(self, left, right):
        for key, count in right.items():
            left[key] = left.get(key, 0) + count
        return left

quality_counts = sc.accumulator(
    {{
        "missing_city": 0,
        "invalid_quantity": 0,
        "invalid_discount": 0,
    }},
    DictAccumulatorParam(),
)
Industry benefit: one job can report several rejection reasons without collecting every rejected record to the Driver.

8. Simple Broadcast Demo

Requirement: enrich every order with product category, manager and cost using a small product-master dictionary.

product_broadcast = sc.broadcast(
    load_product_master()
)

enriched = (
    lines
    .filter(lambda line: line != header)
    .map(parse_order)
    .filter(lambda row: "_parse_error" not in row)
    .map(lambda order: {{
        **order,
        **product_broadcast.value.get(
            order["product_id"],
            {{
                "product_name": "UNKNOWN",
                "category": "UNKNOWN",
                "manager": "UNASSIGNED",
                "cost_price": 0.0,
            }},
        ),
    }})
)
  1. Driver loads products.csv.
  2. Dictionary is broadcast.
  3. Tasks perform local lookups.
  4. Unknown keys use safe fallback values.
  5. No pair-RDD shuffle join is required.

9. Numeric and Custom Accumulator Demo

invalid_records = sc.accumulator(0)
non_completed = sc.accumulator(0)

def validate(order):
    if "_parse_error" in order:
        invalid_records.add(1)
        return False

    if (
        not order["city"]
        or order["quantity"] <= 0
        or not 0 <= order["discount_pct"] <= 100
    ):
        invalid_records.add(1)
        return False

    if order["status"] != "COMPLETED":
        non_completed.add(1)

    return True

Custom Reason Updates

updates = {{}}

if not order["city"]:
    updates["missing_city"] = 1

if order["quantity"] <= 0:
    updates["invalid_quantity"] = 1

if updates:
    quality_counts.add(updates)

11. Best Practices and Anti-Patterns

RecommendedAvoid
Broadcast small read-only data.Broadcasting a huge fact dataset.
Use fallback values for missing lookup keys.Direct dictionary indexing without quality handling.
Read accumulator values after actions.Reading the value inside task logic.
Cache before several actions.Re-executing counter side effects repeatedly.
Use accumulators for diagnostics.Using them as exactly-once business state.
Use DataFrame broadcast joins for structured joins.Confusing join hints with shared variables.
