BigQuery Slot-Based Execution vs Spark Executor Model

Understand how the same retail analytics query is planned, parallelized, shuffled, monitored, scaled and charged in Google BigQuery and Apache Spark.

1. Learning goal

After this tutorial, you should be able to explain why BigQuery asks you to think about queries, stages, slots and reservations, while Spark asks you to think about applications, drivers, executors, cores, memory, jobs, stages and tasks.

Central idea: Both systems split work into parallel units, but BigQuery hides worker lifecycle behind a serverless service. Spark exposes application-level worker processes called executors.

2. First understand it with a restaurant analogy

BigQuery: managed kitchen workstations

You submit an order. The restaurant decides how many temporary workstations are available, assigns work, redistributes it between stages and returns the meal. You do not hire or manage individual cooks.

Workstation capacity ≈ slots

Spark: hired kitchen teams

You start a catering project. A manager obtains teams. Each team has a fixed number of cooks and storage space. The teams remain with your application and execute many individual tasks.

Team process ≈ executor; cooks ≈ executor cores

Do not say: “One BigQuery slot equals one Spark executor.” A slot is a virtual compute unit; an executor is a JVM process with memory and one or more cores.

3. BigQuery slot-based execution

A BigQuery slot is a virtual compute unit used to execute a query or another job. BigQuery determines the number of slots used according to the work, query complexity and available capacity.

SQL job

The user submits GoogleSQL. BigQuery creates an execution plan.

Stages and steps

The plan becomes stages such as read, filter, join, aggregate and sort.

Slots

Slots provide parallel compute to units of work within eligible stages.

Important slot behaviour

  • Slots are allocated by the managed scheduler rather than manually attached to a specific query worker.
  • A query can use different amounts of parallelism during different stages.
  • Stages exchange intermediate data through distributed shuffle.
  • With on-demand analysis you do not provision a cluster; with capacity pricing, reservations are pools of slots assigned to workloads.

4. Spark executor model

A Spark application contains a driver and a set of executor processes acquired through a cluster manager. Executors run tasks and keep data in memory or on disk for that application.

Driver

Creates the Spark session, builds plans, creates jobs and stages, and schedules tasks.

Executor

A worker JVM process allocated to one Spark application, with configured cores and memory.

Task

The smallest scheduled unit. Usually one task processes one input partition in a stage.

Executor parallelism: an executor with four usable cores can normally run roughly four tasks concurrently, subject to configuration and task CPU requirements.

7. How one query flows

SELECT category,
       SUM(quantity * unit_price) AS revenue
FROM retail.orders
WHERE order_date BETWEEN '2026-07-01' AND '2026-07-31'
GROUP BY category
ORDER BY revenue DESC;

BigQuery flow

  1. Parse and validate GoogleSQL.
  2. Prune unrelated date partitions.
  3. Create an execution graph.
  4. Use slot capacity to scan selected columns.
  5. Filter and calculate row revenue.
  6. Shuffle rows by category.
  7. Perform partial and final aggregation.
  8. Sort the small result.

Spark flow

  1. Driver sends SQL to Catalyst.
  2. Logical and physical plans are created.
  3. File pruning and predicate pushdown are attempted.
  4. An action creates a Spark job.
  5. The DAG is split at shuffle boundaries.
  6. Tasks run on executor cores.
  7. Executors shuffle category partitions.
  8. Final tasks aggregate and sort.

8. End-to-end hands-on demo

Use case: A retailer wants July 2026 revenue by product category. Both demos generate equivalent synthetic orders, filter July, aggregate revenue and expose the execution plan.

Part A — BigQuery Sandbox demo

Open BigQuery

In Google Cloud Console, open BigQuery → SQL workspace. Select or create a project. BigQuery Sandbox can run the SQL below without creating a compute cluster.

Create a dataset

CREATE SCHEMA IF NOT EXISTS `YOUR_PROJECT.slot_executor_demo`
OPTIONS(location = 'US');

Create a partitioned retail table

CREATE OR REPLACE TABLE `YOUR_PROJECT.slot_executor_demo.orders`
PARTITION BY order_date
CLUSTER BY category AS
SELECT
  n AS order_id,
  DATE_ADD(DATE '2025-01-01', INTERVAL MOD(n, 730) DAY) AS order_date,
  CONCAT('C', LPAD(CAST(MOD(n, 20000) AS STRING), 5, '0')) AS customer_id,
  ['Electronics','Grocery','Fashion','Furniture','Sports'][OFFSET(MOD(n,5))] AS category,
  1 + MOD(n, 5) AS quantity,
  CAST(10 + MOD(n * 17, 990) AS NUMERIC) AS unit_price
FROM UNNEST(GENERATE_ARRAY(1, 500000)) AS n;

This creates 500,000 rows distributed over 730 dates. Partitioning makes the date filter realistic, while clustering helps category grouping within relevant storage blocks.

Run the analytics query

SELECT
  category,
  ROUND(SUM(quantity * unit_price), 2) AS revenue
FROM `YOUR_PROJECT.slot_executor_demo.orders`
WHERE order_date BETWEEN DATE '2026-07-01' AND DATE '2026-07-31'
GROUP BY category
ORDER BY revenue DESC;

Inspect BigQuery execution

After completion, open Execution details. Observe stages such as table read, aggregate and sort. Select a stage to inspect input/output rows, timing, shuffle and slot-related metrics available in the console.

Check slot milliseconds from job metadata

SELECT
  job_id,
  creation_time,
  total_bytes_processed,
  total_slot_ms,
  ROUND(total_slot_ms / 1000.0, 2) AS total_slot_seconds,
  ROUND(total_slot_ms / NULLIF(TIMESTAMP_DIFF(end_time, start_time, MILLISECOND),0), 2)
    AS average_slots_approx
FROM `region-us`.INFORMATION_SCHEMA.JOBS_BY_USER
WHERE statement_type = 'SELECT'
  AND query LIKE '%slot_executor_demo.orders%'
ORDER BY creation_time DESC
LIMIT 5;

The average is an approximation based on total slot milliseconds divided by elapsed execution milliseconds.

Part B — PySpark local or Databricks demo

Create the Spark session and data

from pyspark.sql import SparkSession, functions as F

spark = (
    SparkSession.builder
    .appName("SlotVsExecutorRetailDemo")
    .master("local[4]")       # remove this line in Databricks
    .config("spark.sql.shuffle.partitions", "8")
    .getOrCreate()
)
spark.sparkContext.setLogLevel("WARN")

orders = (
    spark.range(1, 500001)
    .withColumnRenamed("id", "order_id")
    .withColumn(
        "order_date",
        F.date_add(F.lit("2025-01-01").cast("date"),
                   (F.col("order_id") % 730).cast("int"))
    )
    .withColumn(
        "customer_id",
        F.concat(F.lit("C"), F.lpad((F.col("order_id") % 20000).cast("string"), 5, "0"))
    )
    .withColumn(
        "category",
        F.element_at(
            F.array(*[F.lit(x) for x in ["Electronics","Grocery","Fashion","Furniture","Sports"]]),
            ((F.col("order_id") % 5) + 1).cast("int")
        )
    )
    .withColumn("quantity", ((F.col("order_id") % 5) + 1).cast("int"))
    .withColumn("unit_price", (F.lit(10) + ((F.col("order_id") * 17) % 990)).cast("decimal(10,2)"))
    .repartition(8, "order_date")
)

orders.createOrReplaceTempView("orders")
print("Input partitions:", orders.rdd.getNumPartitions())

Execute the same business logic

result = spark.sql("""
SELECT category,
       ROUND(SUM(quantity * unit_price), 2) AS revenue
FROM orders
WHERE order_date BETWEEN DATE '2026-07-01' AND DATE '2026-07-31'
GROUP BY category
ORDER BY revenue DESC
""")

result.explain("formatted")
result.show(truncate=False)

Keep the application open for Spark UI

input("Open http://localhost:4040, inspect Jobs/Stages/Executors, then press Enter...")
spark.stop()

In Databricks, open the Spark UI from the cluster or query details. In local PySpark, use http://localhost:4040 while the application is running.

Run with explicit executors on a real cluster

spark-submit \
  --master yarn \
  --deploy-mode cluster \
  --num-executors 3 \
  --executor-cores 2 \
  --executor-memory 2g \
  slot_vs_executor_demo.py

At most about six ordinary one-CPU tasks can run simultaneously across these executors, assuming resources are available and no additional constraints apply.

Expected Spark physical-plan ideas

Scan/Range
  → Filter order_date
  → Project quantity * unit_price
  → HashAggregate (partial)
  → Exchange hashpartitioning(category)   <-- shuffle boundary
  → HashAggregate (final)
  → Exchange rangepartitioning(revenue)   <-- ordering shuffle
  → Sort
  → Result

10. Performance and scaling

BigQuery scaling levers

  • Reduce bytes with partition pruning and column selection.
  • Filter before joins and aggregations.
  • Use clustering where access patterns justify it.
  • Manage concurrency and capacity with reservations/assignments when using capacity pricing.
  • Inspect slot contention and stage bottlenecks.

Spark scaling levers

  • Choose input and shuffle partition counts.
  • Configure executor instances, cores and memory.
  • Use dynamic allocation or cluster autoscaling where supported.
  • Handle skew, spills, broadcast joins and small files.
  • Cache only reused data that fits the workload.
Parallelism limit: Giving either platform more compute cannot remove a serial bottleneck, severe skew, tiny remaining stage or inefficient query plan.

12. Where to use each model

Prefer BigQuery when

  • The main workload is warehouse-style SQL analytics.
  • You want minimal infrastructure management.
  • Analysts need ad hoc queries and BI access.
  • Compute should scale behind a service boundary.
  • Data is primarily organized for analytical scanning.

Prefer Spark when

  • You need programmable ETL beyond SQL.
  • The pipeline combines SQL, Python/Scala, ML or streaming.
  • You need control over partitioning, caching and execution resources.
  • You process across a data lake and multiple formats/systems.
  • Custom libraries and application logic are central.

Memory aid: BigQuery = “submit query, service schedules capacity.” Spark = “start application, driver schedules tasks on executors.”

14. Interview questions and answers

1. What is a BigQuery slot?

A virtual compute unit used by BigQuery for query and job execution. The scheduler assigns parallel capacity according to work and available resources.

2. What is a Spark executor?

A process launched for a Spark application on a worker node. It runs tasks and provides memory and storage for application data.

3. Is a BigQuery slot equivalent to a Spark executor?

No. The closer Spark-side capacity analogy is executor cores participating in task execution, but even that is not a strict hardware or performance equivalence.

4. What causes stages in both systems?

Distributed data dependencies and operations such as joins, grouping and sorting often require data exchange. BigQuery represents query work as stages; Spark divides a job into stages at shuffle boundaries.

5. Who schedules work?

BigQuery uses managed internal schedulers. In Spark, the driver schedules tasks on executors after obtaining resources from the cluster manager.

6. Why can more slots or executors fail to improve speed?

The workload may be limited by skew, serial stages, small input, inefficient joins, I/O, or insufficient partitions.

7. How do you prove Spark executors executed the work?

Use the Spark UI Executors and Stages tabs to inspect executor IDs, active/completed tasks, input, shuffle, memory, disk and runtime metrics.

8. How do you measure BigQuery slot consumption?

Inspect execution details and query job metadata such as total_slot_ms in INFORMATION_SCHEMA job views.

9. What is dynamic allocation in Spark?

A mechanism that adjusts executor count based on pending work and idleness, when supported and correctly configured.

10. What is a BigQuery reservation?

A pool used to manage and isolate slot capacity for assigned projects, folders or organizations under capacity-based workload management.

16. Cleanup and cost control

BigQuery

DROP SCHEMA `YOUR_PROJECT.slot_executor_demo` CASCADE;

Spark

  • Run spark.stop() for a local application.
  • Terminate temporary Dataproc/EMR/VM clusters after the lab.
  • Stop or delete temporary Databricks compute according to workspace policy.
  • Remove temporary files or tables created for the demo.
Trainer conclusion: BigQuery gives capacity as a managed slot abstraction that can vary across query stages. Spark gives an application a visible pool of executor processes, each with memory and cores, and schedules partition-level tasks on those cores.
