1. What is Partition Pruning?

Partition pruning is BigQuery's ability to read only the partitions required by a query and skip the rest.

Partitioning divides the table. Pruning skips the divisions that the query does not need.

Assume a sales table contains one year of orders and is partitioned by order_date. A query asking only for July 2026 can scan the July partitions instead of reading the entire year.

Without pruning

BigQuery scans all dates, then filters rows. More bytes are processed.

With pruning

BigQuery identifies the required date partitions first and reads only those partitions.

3. Where Should We Use It?

ScenarioSuitable partition columnExample filter
Retail orders and daily reportsorder_dateLast 7 days or a selected month
Bank transactionstransaction_dateCurrent statement period
Application logsevent_timestamp or ingestion timeErrors from the last hour/day
IoT sensor readingsreading_timestampReadings for a date range
Customer or account rangesInteger IDID between defined boundaries
Choose a partition column that appears regularly in query filters. A partitioned table alone does not guarantee pruning; the query must provide an eligible filter.

When partitioning may not help much

  • The table is very small.
  • Most queries scan nearly every partition.
  • The chosen column is rarely filtered.
  • The partitioning creates too many tiny partitions; clustering may be more suitable.

4. Complete BigQuery Console Lab

Use case A retail company stores orders for 365 days. Management usually requests reports for a particular week or month.

Architecture

Open BigQuery

Open Google Cloud Console → select a project → use the navigation menu → BigQuery → SQL workspace. BigQuery Sandbox users can perform this lab without enabling billing, subject to Sandbox limits.

Create a dataset

In the Explorer panel, click the three dots beside the project → Create dataset. Dataset ID: pruning_demo. Select a suitable location and click Create dataset.

CREATE SCHEMA IF NOT EXISTS `YOUR_PROJECT_ID.pruning_demo`
OPTIONS(location = 'US');

Replace YOUR_PROJECT_ID. Use this SQL alternative only when the chosen dataset location is US.

Create a non-partitioned sales table

CREATE OR REPLACE TABLE `YOUR_PROJECT_ID.pruning_demo.retail_orders_nonpartitioned` AS
SELECT
  FORMAT('ORD-%09d', row_number) AS order_id,
  DATE_ADD(DATE '2025-08-01', INTERVAL day_offset DAY) AS order_date,
  10000 + MOD(row_number, 50000) AS customer_id,
  ['Electronics','Grocery','Fashion','Home','Sports'][OFFSET(MOD(row_number, 5))] AS category,
  ['Bengaluru','Chennai','Mumbai','Delhi','Hyderabad'][OFFSET(MOD(row_number, 5))] AS city,
  1 + MOD(row_number, 5) AS quantity,
  CAST(100 + MOD(row_number * 37, 50000) AS NUMERIC) AS unit_price,
  ROUND(CAST((1 + MOD(row_number, 5)) * (100 + MOD(row_number * 37, 50000)) AS NUMERIC), 2) AS sales_amount
FROM (
  SELECT
    day_offset,
    item_offset,
    day_offset * 2000 + item_offset + 1 AS row_number
  FROM UNNEST(GENERATE_ARRAY(0, 364)) AS day_offset
  CROSS JOIN UNNEST(GENERATE_ARRAY(0, 1999)) AS item_offset
);

This creates approximately 730,000 rows covering August 1, 2025 through July 31, 2026.

Create the partitioned version

CREATE OR REPLACE TABLE `YOUR_PROJECT_ID.pruning_demo.retail_orders_partitioned`
PARTITION BY order_date
OPTIONS (
  description = 'Retail orders partitioned by order_date',
  require_partition_filter = TRUE
) AS
SELECT *
FROM `YOUR_PROJECT_ID.pruning_demo.retail_orders_nonpartitioned`;

require_partition_filter = TRUE protects users from accidentally running queries without an eligible partition filter.

Check record counts

SELECT 'nonpartitioned' AS table_type, COUNT(*) AS row_count
FROM `YOUR_PROJECT_ID.pruning_demo.retail_orders_nonpartitioned`
UNION ALL
SELECT 'partitioned', COUNT(*)
FROM `YOUR_PROJECT_ID.pruning_demo.retail_orders_partitioned`
WHERE order_date BETWEEN DATE '2026-07-01' AND DATE '2026-07-31';

Because the partitioned table requires a filter, its count in this query is intentionally limited to July.

Run the report on the non-partitioned table

SELECT
  category,
  SUM(sales_amount) AS total_sales
FROM `YOUR_PROJECT_ID.pruning_demo.retail_orders_nonpartitioned`
WHERE order_date BETWEEN DATE '2026-07-01' AND DATE '2026-07-31'
GROUP BY category
ORDER BY total_sales DESC;

Before clicking Run, observe the estimated bytes processed shown by the console.

Run the same report on the partitioned table

SELECT
  category,
  SUM(sales_amount) AS total_sales
FROM `YOUR_PROJECT_ID.pruning_demo.retail_orders_partitioned`
WHERE order_date BETWEEN DATE '2026-07-01' AND DATE '2026-07-31'
GROUP BY category
ORDER BY total_sales DESC;

The business result should match, but BigQuery can prune all partitions except July.

Inspect the partitions

SELECT
  partition_id,
  total_rows,
  total_logical_bytes,
  last_modified_time
FROM `YOUR_PROJECT_ID.pruning_demo.INFORMATION_SCHEMA.PARTITIONS`
WHERE table_name = 'retail_orders_partitioned'
ORDER BY partition_id;

This metadata view returns one row for each partition.

6. BigQuery Partition Types

TypeDescriptionFilter for pruning
Time-unit columnPartition by a DATE, TIMESTAMP, or DATETIME column.Filter the partitioning column.
Ingestion timePartition based on when BigQuery ingests the row.Filter _PARTITIONTIME or _PARTITIONDATE.
Integer rangePartition an integer column using configured start, end, and interval values.Filter the integer partition column.

Ingestion-time example

SELECT *
FROM `YOUR_PROJECT_ID.pruning_demo.events_by_ingestion`
WHERE _PARTITIONDATE BETWEEN DATE '2026-07-01' AND DATE '2026-07-07';

Integer-range example

CREATE TABLE `YOUR_PROJECT_ID.pruning_demo.customers_by_id`
(
  customer_id INT64,
  customer_name STRING,
  city STRING
)
PARTITION BY RANGE_BUCKET(customer_id, GENERATE_ARRAY(0, 100000, 10000));

7. Common Mistakes and Fixes

Mistake: no partition filter

SELECT *
FROM `...retail_orders_partitioned`;

With required filtering enabled, BigQuery rejects this query.

Fix

SELECT *
FROM `...retail_orders_partitioned`
WHERE order_date = DATE '2026-07-24';

Mistake: dynamic expression around the partition column

Complex transformations can make pruning harder or prevent it. Prefer a direct comparison against a constant range.

Preferred pattern

WHERE order_date >= DATE '2026-07-01'
  AND order_date < DATE '2026-08-01'

Mistake: filtering another column

WHERE city='Chennai' does not prune date partitions.

Fix: combine filters

WHERE order_date BETWEEN DATE '2026-07-01' AND DATE '2026-07-31'
  AND city = 'Chennai'

Partitioning plus clustering

For frequent queries by date, city, and category, partition by date and cluster within each partition by selected dimensions.

CREATE OR REPLACE TABLE `YOUR_PROJECT_ID.pruning_demo.retail_orders_optimized`
PARTITION BY order_date
CLUSTER BY city, category AS
SELECT *
FROM `YOUR_PROJECT_ID.pruning_demo.retail_orders_nonpartitioned`;

8. Best Practices

  1. Partition using a column commonly used in filters.
  2. Use direct filters on the partitioning column or ingestion-time pseudocolumn.
  3. Enable require_partition_filter for large production tables.
  4. Select only required columns; avoid unnecessary SELECT *.
  5. Use clustering for additional selective filters inside partitions.
  6. Check estimated bytes before running expensive queries.
  7. Use INFORMATION_SCHEMA.PARTITIONS to inspect partition health and size.

9. Interview Questions and Answers

1. What is the difference between partitioning and partition pruning?

Partitioning divides a table into segments. Partition pruning is the query-time process of skipping segments that cannot satisfy the partition filter.

2. Does every query on a partitioned table use pruning?

No. The query needs an eligible filter on the partitioning column or the relevant ingestion-time pseudocolumn.

3. Why does pruning reduce cost?

Under on-demand pricing, fewer bytes processed generally means a lower query charge.

4. What does require_partition_filter do?

It requires queries to include a filter suitable for partition elimination, helping prevent accidental broad scans.

5. Partitioning versus clustering?

Partitioning creates table segments using a partition key. Clustering organizes storage blocks within a table or partition using clustered columns. They can be combined.

6. Which pseudocolumn is used for ingestion-time partitioning?

_PARTITIONTIME; for daily granularity, _PARTITIONDATE is also available.

7. How can you verify partitions?

Query the dataset's INFORMATION_SCHEMA.PARTITIONS view.

8. What is a practical date filter style?

Use a direct half-open range, for example order_date >= DATE '2026-07-01' AND order_date < DATE '2026-08-01'.
