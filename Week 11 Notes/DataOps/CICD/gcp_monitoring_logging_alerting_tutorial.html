1. What are we trying to build?

Assume a retail company loads daily sales. Cloud Composer / Managed Airflow orchestrates the workflow, Dataflow transforms records, BigQuery stores the cleaned result, and the operations team needs to know immediately when something fails.

Cloud Storage (sales.csv) │ ▼ Managed Airflow / Cloud Composer │ orchestrates ▼ Dataflow / Apache Beam │ transforms ▼ BigQuery (retail.sales_clean) OBSERVABILITY LAYER ────────────────── Dataflow + Airflow logs │ ▼ Cloud Logging / Logs Explorer │ ├───────────────┐ ▼ ▼ Log-based metric Direct log alert failure_count │ ▼ Cloud Monitoring │ ▼ Alerting Policy │ threshold > 0 ▼ Incident │ ▼ Email notification │ ▼ Engineer → Logs → Root cause → Fix → Rerun
Teaching objective: students should understand the difference between observing health, investigating detail, turning business-specific log events into metrics, and notifying an engineer when a threshold is crossed.

2. Monitoring vs Logging — the most important foundation

Monitoring

Monitoring answers: “Is the system healthy?”

It deals mainly with measurable values called metrics.

  • Job state
  • CPU utilization
  • worker count
  • records processed
  • system lag
  • DAG/task failures

Logging

Logging answers: “What exactly happened, and why?”

It stores timestamped execution events.

  • Python exceptions
  • permission denied
  • table not found
  • worker messages
  • Airflow task traceback
QuestionMonitoringLogging
PurposeDetect abnormal health or performanceInvestigate detailed execution events
Typical dataNumbers/time seriesText/structured log entries
ExampleFailed jobs = 1BigQuery table not found
Used forDashboards, SLOs, alertsTroubleshooting, audit, root cause
Simple analogy: the warning light on a car dashboard is monitoring. The diagnostic code explaining the engine fault is logging.

3. Monitoring and Logging for Dataflow

Dataflow is Google Cloud's managed service for executing Apache Beam batch and streaming pipelines. For operations, there are two main places you should teach:

Dataflow Job details

Best for one specific pipeline/job: job state, graph, stages, throughput, worker/resource metrics, I/O and execution progress.

Cloud Monitoring

Best for cross-service metrics, dashboards, historical charts, alert conditions, incidents and notification channels.

Important Dataflow signals

SignalWhat it tells youReal-world concern
Job status / FailedWhether a batch/streaming job failedDaily load missing
Element count / throughputHow much data is flowingZero or unexpectedly low volume
CPU / worker utilizationResource pressurePipeline slower than expected
System lagHow far streaming processing is behindSLA breach in near-real-time use cases
Worker count / autoscalingScale behaviorCost or insufficient parallelism

GUI path

Google Cloud Console → Dataflow → Jobs → select job

Show trainees: Job info → Execution details / pipeline graph → Job metrics → Logs. The exact tab names can vary slightly as the console evolves, but the job details page remains the operational home for a single Dataflow job.

4. Monitoring and Logging for Cloud Composer / Managed Airflow

Google now presents the newer Composer experience as Managed Airflow in parts of the console and documentation. The core operational concepts are still Apache Airflow DAGs, runs, tasks, scheduler, workers and logs.

What should you monitor?

DAG runs

Success/failure, duration, schedule adherence.

Task instances

Failed tasks, retries, long-running tasks, queueing.

Environment health

Scheduler/workers and managed environment health/performance.

Two useful interfaces

Managed Airflow environment monitoringEnvironment/DAG-level metrics and managed-service health
Apache Airflow UIGrid/Graph views, task instance details, run history, task logs

5. Cloud Logging and Logs Explorer

Cloud Logging centralizes logs produced by Google Cloud services and your applications. Logs Explorer is the GUI used to search and inspect them.

GUI path

Navigation menu → Observability → Logging → Logs Explorer

Starter queries

severity>=ERROR

Search a custom application failure signature:

"SALES_PIPELINE_FAILED"

You can combine filters as your production setup matures, for example by resource type, region, environment, job, DAG or task labels.

Trainer rule: always confirm that the Logs Explorer query returns the exact failure log before using that query to create a log-based metric or alert. Otherwise you can create a metric that never increments.

6. What is a Log-based Metric?

A log-based metric converts matching log entries into time-series metric data that Cloud Monitoring can chart and alert on.

Logs Explorer "SALES_PIPELINE_FAILED" │ ▼ Counter log-based metric sales_pipeline_failure_count │ ▼ 0, 1, 2, 3 ... failures over time │ ├── chart in Metrics Explorer └── alert when count > 0

Types

TypeUseExample
CounterCount matching eventsNumber of failed tasks
DistributionExtract numeric values and analyze their distributionProcessing time / latency
BooleanRecord whether matching log events occurredSpecific error condition occurred
For this lab use Counter. It is the easiest way to demonstrate “one matching failure log = one increment”.

7. Alerting Policies — detailed explanation

An Alerting Policy is the operational rule that tells Cloud Monitoring when a metric or log condition is serious enough to create an incident and notify people.

RESOURCE / PIPELINE │ ▼ METRIC failure_count │ ▼ CONDITION "above threshold" │ ▼ THRESHOLD > 0 │ ▼ RETEST WINDOW / EVALUATION condition must be true for chosen period │ ▼ INCIDENT │ ▼ NOTIFICATION CHANNEL Email / Slack / PagerDuty / Pub/Sub / etc. │ ▼ RUNBOOK / DOCUMENTATION What should the engineer do?

7.1 Parts of an alert policy

PartMeaningRetail example
MetricThe signal being watchedsales_pipeline_failure_count
Filter/resourceWhich environment/job/metric seriesRetail Composer failures only
ConditionComparison ruleAbove threshold
ThresholdBoundary separating normal from abnormal> 0
AggregationHow points are combinedCount/sum over a short window
Retest windowHow long the condition must remain true0–1 min for classroom; longer for noisy production signals
Notification channelWho/where is notifiedData engineering support email
DocumentationRunbook details in incident/notificationOpen DAG → failed task → logs → fix → rerun

7.2 Why threshold design matters

Too sensitive

Every tiny transient issue pages the team. Result: alert fatigue.

Too weak

Real failures are ignored until users report missing data. Result: late incident detection.

7.3 Real-world design examples

ScenarioBetter conditionWhy
Daily batch pipelineFailed = 1A single failure is important
Streaming laglag > 5 min for 10 minAvoid alerting on momentary spikes
Bad recordserror_count > 100 in 5 minSome bad rows may be acceptable
Airflow task failurefailure_count > 0Critical orchestration task should succeed
Pipeline SLAruntime beyond SLAJob can be “running” yet still be operationally bad

7.4 Incident lifecycle

When the condition is met, Cloud Monitoring opens an incident. The incident records which policy fired, which time series violated the condition, and timing/details useful for investigation. When the condition clears, the incident can close based on policy behavior.

7.5 Notification channel

A notification channel controls how people are contacted. In this tutorial we use Email. Production teams often also use Slack, PagerDuty, Webhooks, Pub/Sub or other integrations.

Best practice: put a short runbook directly in the alert policy documentation. An engineer receiving the notification should immediately know: what failed, where to open the service, which logs to inspect, and what validation to perform after the fix.

11. Demo 2 — deliberately fail a Composer / Managed Airflow task

Use a very simple DAG so that the failure is obvious.

from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

def extract_sales():
    print("SALES_EXTRACT_STARTED")
    print("SALES_EXTRACT_COMPLETED")

def transform_sales():
    print("SALES_TRANSFORMATION_STARTED")
    raise Exception("SALES_PIPELINE_FAILED: Invalid sales transformation")

def load_sales():
    print("SALES_LOAD_STARTED")
    print("SALES_LOAD_COMPLETED")

with DAG(
    dag_id="retail_sales_monitoring",
    start_date=datetime(2026, 1, 1),
    schedule="@daily",
    catchup=False
) as dag:

    extract = PythonOperator(
        task_id="extract_sales",
        python_callable=extract_sales
    )

    transform = PythonOperator(
        task_id="transform_sales",
        python_callable=transform_sales
    )

    load = PythonOperator(
        task_id="load_sales",
        python_callable=load_sales
    )

    extract >> transform >> load

Run it in the GUI

1
Managed Airflow / Composer → Environments → your environment → DAGs
2
Open retail_sales_monitoring.
3
Trigger the DAG manually.
4
Expected state:
extract_sales     SUCCESS
transform_sales   FAILED
load_sales        NOT EXECUTED / upstream failed
5
Open the failed transform_sales task → Logs. Find SALES_PIPELINE_FAILED.
6
Now open Logging → Logs Explorer and search:
"SALES_PIPELINE_FAILED"
At this point the class has seen the same failure in two views: Airflow task logs for the specific task, and centralized Cloud Logging for cross-environment investigation.

SLA example

Pipeline starts at 2:00 AM and must finish before 6:00 AM. At 5:30 AM it is still running. Nothing has “failed,” but the business SLA is in danger. This is why mature monitoring covers failure, latency, lag, throughput, volume, duration and data quality.

21. Quick knowledge check

1. What is the main difference between monitoring and logging?
Monitoring summarizes system health/performance using metrics. Logging stores detailed events used to understand what happened and why.

2. Why create a log-based metric?
To convert selected log events, including application-specific failure messages, into time-series metrics that can be charted and used in alert conditions.

3. What does threshold > 0 mean for sales_pipeline_failure_count?
Zero is normal. One or more matching failures makes the condition abnormal and can create an incident.

4. What is the role of a notification channel?
It defines how people or systems receive notifications when an alerting policy creates an incident, for example by email.

5. Why include runbook documentation in an alert policy?
So the on-call engineer receives immediate investigation and recovery instructions instead of wasting time figuring out where to start.
