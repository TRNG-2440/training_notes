1. Learning Outcomes

After this session, trainees should be able to explain and demonstrate:

  • Why DataOps is needed even when individual ETL/ELT tools already work.
  • How collaboration, automation, quality gates, observability, version control and continuous improvement form one lifecycle.
  • How a dbt change moves safely from developer laptop → pull request → CI → test schema → production.
  • How an Airflow DAG moves from Git → syntax/import tests → unit tests → deployment to a managed Airflow environment.
  • How automated tests stop bad data before it reaches Snowflake Gold tables and Power BI dashboards.
  • How to decide whether a failure is a code issue, infrastructure issue, data quality issue, SLA issue or downstream BI issue.
Trainer sentence: “Data engineering builds the pipeline. DataOps builds the safe, repeatable way in which the team changes, tests, deploys and operates that pipeline.”

Traditional approach

A developer writes an ETL job, manually copies the code to production, runs it, and checks the result. This may work with one developer and one pipeline, but it becomes dangerous when many engineers, datasets and business reports depend on each other.

DataOps approach

Every change is versioned, reviewed, tested automatically, deployed consistently, monitored after release and improved based on operational feedback.

QuestionTraditional data engineeringDataOps-oriented engineering
Where is code?Laptop/server foldersGit repository
How is it reviewed?Manual or ad hocPull request + reviewers
How is it tested?Developer runs queriesAutomated quality gates
How is it deployed?Copy/upload manuallyCI/CD pipeline
How are failures found?User reports dashboard issueMonitoring + alerting + SLAs
How do we recover?Fix directly in prodRollback/redeploy/reprocess

Step 1 — Plan

Convert the business requirement into measurable engineering expectations.

Business: "Sales dashboard must be ready every morning."
Engineering:
- Airflow pipeline starts 05:30
- dbt transformations complete by 06:30
- validation completes by 06:40
- Power BI refresh starts after successful validation
- SLA breach alert if pipeline is still incomplete at 06:45

Step 2 — Develop

Develop in isolated branches and non-production schemas. Example:

feature/add-return-rate
  ├── models/staging/stg_orders.sql
  ├── models/marts/fct_sales.sql
  ├── models/schema.yml
  └── tests/assert_revenue_non_negative.sql

Step 3 — Version

Git provides an auditable history. Every dbt model, Airflow DAG, Python script, test and configuration should be version-controlled unless it contains secrets.

Step 4 — Test

Run inexpensive tests early. Run integration tests before deployment. Run production data-quality checks after deployment.

Step 5 — Release

Approved changes are merged and deployed through controlled automation rather than laptop-to-production copying.

Step 6 — Operate

Airflow schedules jobs, handles dependencies and retries, while warehouse and processing systems execute the work.

Step 7 — Monitor

Observe availability, freshness, task duration, data volume, quality, cost and SLA.

Step 8 — Improve

Use incidents and trend data to improve tests, retry policies, alert thresholds, model design and capacity.

B. Automation

Automation does not only mean scheduling an ETL job. In DataOps, automation covers:

  • environment setup, dependency installation and validation;
  • linting and static checks;
  • dbt parsing/build/test;
  • Airflow DAG import tests;
  • deployment;
  • quality validation;
  • alerting and incident creation;
  • rollback or controlled reprocessing.

7. CI/CD Pipeline for dbt

The objective is simple: a developer should not be able to merge a dbt model that cannot compile or that breaks required data tests.

CI flow

Change SQL
→
PR
→
dbt deps
→
dbt parse
→
dbt build
→
Review

Important dbt commands

# Install project packages
dbt deps

# Validate project structure / parsing
dbt parse

# Execute models and tests in dependency order
dbt build

# Run only tests
dbt test

# Generate documentation artifacts
dbt docs generate

Example dbt model

-- models/marts/fct_sales.sql
select
    order_id,
    order_date,
    customer_id,
    product_id,
    quantity,
    unit_price,
    quantity * unit_price as gross_sales
from {{ ref('stg_orders') }}
where order_status != 'CANCELLED'

Generic dbt tests

# models/schema.yml
version: 2

models:
  - name: fct_sales
    columns:
      - name: order_id
        tests:
          - not_null
          - unique

      - name: customer_id
        tests:
          - not_null

      - name: gross_sales
        tests:
          - not_null

Singular business test

-- tests/assert_sales_not_negative.sql
select *
from {{ ref('fct_sales') }}
where gross_sales < 0

dbt singular tests are designed so that zero returned rows means the test passes.

GitHub Actions — dbt CI example

name: dbt-ci

on:
  pull_request:
    paths:
      - "dbt/**"

jobs:
  dbt-test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - name: Install dbt
        run: |
          pip install dbt-core dbt-snowflake

      - name: Install dbt packages
        working-directory: dbt
        run: dbt deps

      - name: Parse project
        working-directory: dbt
        run: dbt parse

      - name: Build and test
        working-directory: dbt
        env:
          SNOWFLAKE_ACCOUNT: ${{ secrets.SNOWFLAKE_ACCOUNT }}
          SNOWFLAKE_USER: ${{ secrets.SNOWFLAKE_USER }}
          SNOWFLAKE_PASSWORD: ${{ secrets.SNOWFLAKE_PASSWORD }}
        run: dbt build --target ci
Trainer note: Never put Snowflake passwords, private keys, GCP service-account keys or tokens directly in YAML committed to Git. Use your CI platform’s secret mechanism or workload identity.

What should fail a dbt PR?

  • SQL cannot compile.
  • Referenced model does not exist.
  • Required uniqueness/not-null test fails.
  • Business rule test fails.
  • Linting/formatting policy fails, if enforced.
  • Model unexpectedly modifies protected production objects.

8. CI/CD Pipeline for Apache Airflow / Managed Airflow

Airflow code is production application code. A DAG should be tested before it reaches the scheduler.

CI flow for DAGs

Edit DAG
→
PR
→
Python lint
→
Import test
→
DAG tests
→
Deploy

Sample Airflow DAG

from datetime import datetime
from airflow import DAG
from airflow.operators.python import PythonOperator

def validate_source():
    print("Source validation passed")

def run_dbt():
    print("Trigger dbt build")

with DAG(
    dag_id="retail_daily_pipeline",
    start_date=datetime(2026, 1, 1),
    schedule="30 5 * * *",
    catchup=False,
    tags=["retail", "dataops"]
) as dag:

    validate = PythonOperator(
        task_id="validate_source",
        python_callable=validate_source
    )

    transform = PythonOperator(
        task_id="run_dbt",
        python_callable=run_dbt
    )

    validate >> transform

Very basic DAG import test

# airflow/tests/test_retail_dag.py
from airflow.models import DagBag

def test_no_import_errors():
    dag_bag = DagBag(dag_folder="airflow/dags", include_examples=False)
    assert len(dag_bag.import_errors) == 0, dag_bag.import_errors

def test_expected_dag_exists():
    dag_bag = DagBag(dag_folder="airflow/dags", include_examples=False)
    assert "retail_daily_pipeline" in dag_bag.dags

Dependency test

def test_retail_dependencies():
    dag_bag = DagBag(dag_folder="airflow/dags", include_examples=False)
    dag = dag_bag.get_dag("retail_daily_pipeline")

    validate = dag.get_task("validate_source")
    transform = dag.get_task("run_dbt")

    assert "run_dbt" in validate.downstream_task_ids
    assert "validate_source" in transform.upstream_task_ids

1. Code/static tests

Purpose: catch errors without processing production data.

2. Schema tests

Expected order schema:

order_ts       TIMESTAMP
customer_id    STRING
product_id     STRING
quantity       INTEGER
unit_price     NUMBER

If Dataflow suddenly receives quantity="ABC", the record should be rejected/quarantined or fail a contract depending on the design.

3. Data quality tests

4. PySpark unit test example

from pyspark.sql import SparkSession
from pyspark.sql.functions import col

def add_gross_sales(df):
    return df.withColumn("gross_sales", col("quantity") * col("unit_price"))

def test_add_gross_sales():
    spark = SparkSession.builder.master("local[1]").getOrCreate()

    df = spark.createDataFrame(
        [(1, 2, 50.0)],
        ["order_id", "quantity", "unit_price"]
    )

    actual = add_gross_sales(df).collect()[0]["gross_sales"]

    assert actual == 100.0

SELECT

10. Monitoring and Observability

Monitoring asks whether known conditions are healthy. Observability helps engineers investigate why the system behaves unexpectedly.

Minimum dashboard for the retail pipeline

Pipeline success rate
Successful DAG runs / total runs
Freshness
Time since latest source transaction
Runtime
Current duration vs 7-day baseline
Row count
Today vs expected range
DQ failures
Number of failed tests
SLA status
Will dashboard be ready by 7 AM?

Useful alert rules

CRITICAL:
- DAG failed after retries
- dbt critical test failed
- no source data received
- dashboard publication SLA breached

WARNING:
- row count changed > 30%
- runtime > 150% of rolling baseline
- retry count increased
- warehouse cost unusually high
Avoid alert fatigue: If every retry sends a critical page, engineers will learn to ignore alerts. Alert on actionable conditions and separate warning signals from business-impacting incidents.

11. Failure Scenarios — Teach Trainees How to Think

Scenario 1 — Airflow task is green, Power BI numbers are wrong

Why? Orchestration success only means the task completed. It does not guarantee business correctness.

Fix: Add reconciliation/data tests before the publish/refresh step.

Scenario 2 — dbt model compiles but duplicates appear

Why? Compilation validates SQL structure, not uniqueness.

Fix: Add unique test on the business key and investigate join grain.

Scenario 3 — PR works, production fails

Possible causes: missing production permissions, environment-specific variable, missing connection, larger data volume, different warehouse role or package mismatch.

Fix: Environment parity, deployment validation, least-privilege service identities, pre-prod testing.

Scenario 4 — Dataflow receives malformed records

Bad design: silently discard them.

Better design: validate → send invalid records to dead-letter/quarantine → count failures → alert if threshold exceeded.

Scenario 5 — Pipeline retries 5 times for a data-quality failure

Retries help transient infrastructure/network issues. They usually do not repair a deterministic bad-data condition.

Rule: Do not treat every failure as retryable. Classify errors.

Scenario 6 — A developer changes a column name used by Power BI

This is a data-contract breaking change. Detect it before production using schema/contract tests and dependency review.

15. Interview Questions and Answers

1. What is DataOps?

DataOps is an engineering and operating approach that applies collaboration, automation, testing, version control, continuous delivery, monitoring and continuous improvement to data pipelines and data products.

2. How is DataOps different from DevOps?

They share software-engineering practices, but DataOps adds strong emphasis on data quality, freshness, lineage, schema changes, reconciliation and trustworthy downstream analytical outputs.

3. Why is CI important for dbt?

It validates model changes before merge by parsing/building the changed project and executing tests in a safe environment.

4. What is the difference between dbt run, dbt test and dbt build?

dbt run primarily executes models; dbt test executes tests; dbt build runs selected resources such as models and tests in dependency-aware order and is often convenient for CI validation.

5. What is an Airflow DAG import test?

It loads DAG files through Airflow's DAG loading mechanism and verifies that they can be parsed/imported without errors before deployment.

6. Is a successful Airflow DAG enough to guarantee correct data?

No. A task can succeed technically while producing incorrect business data. Data-quality and reconciliation checks are required.

7. What is a data-quality gate?

A mandatory validation stage that must pass before data is promoted or published to consumers.

8. Give examples of automated data tests.

Not-null, uniqueness, referential integrity, accepted values, freshness, row-count thresholds, reconciliation and schema-contract validation.

9. Why use a separate schema for CI?

To avoid PR tests modifying shared production tables and to enable parallel developer validation.

10. What should be stored in Git?

Pipeline code, DAGs, dbt models, tests, configuration templates, documentation and deployment workflow definitions. Secrets should not be committed.

11. Retry or fail immediately for duplicate business keys?

Usually fail the quality gate; retrying will not repair deterministic bad data unless the source itself is expected to self-correct.

12. What is data freshness?

The measure of how recent the available data is relative to an expected arrival or business SLA.

13. Why do we monitor row counts?

Unexpected drops or spikes may indicate missing source partitions, duplication, upstream failures or logic changes.

14. What is reconciliation?

Comparing source and target business totals/counts to confirm that processing has not lost, duplicated or distorted data beyond an accepted tolerance.

15. What is continuous delivery versus continuous deployment?

Continuous delivery keeps changes deployable and may require approval before production; continuous deployment automatically releases changes after required gates pass.

16. Why test DAG dependencies?

A DAG may import correctly but still have incorrect task ordering. Dependency tests validate intended orchestration logic.

17. What should happen if a critical dbt test fails in production?

Stop dependent publish steps, preserve diagnostic evidence, alert the responsible team and follow the recovery/reprocessing runbook.

18. How does Power BI fit into DataOps?

Power BI is a downstream consumer. Its refresh should be driven by trusted, validated data rather than fixed timing that ignores upstream pipeline state.

19. Why are managed Airflow services useful?

They reduce infrastructure-management burden while preserving Airflow's orchestration model, allowing teams to focus more on DAGs, dependencies and operations.

20. Give one example of continuous improvement in DataOps.

After an incident caused by duplicate orders, add a uniqueness test in CI and production so the same class of defect is automatically detected in future.
